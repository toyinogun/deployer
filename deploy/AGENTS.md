# deploy

The Kubernetes manifests for the control plane, applied by ArgoCD into `deployer-system`. Governing spec: [docs/specs/0003-cluster-foundation/index.md](../docs/specs/0003-cluster-foundation/index.md). File by file detail, the first apply steps, and the hand run checks live in [README.md](README.md).

## Layout

- [kustomization.yaml](kustomization.yaml): the apply order. A new manifest is invisible to ArgoCD until it is listed here.
- [namespace.yaml](namespace.yaml), [rbac.yaml](rbac.yaml), [admission-policy.yaml](admission-policy.yaml): the namespace, the service account rights, and the fence around them.
- [pvc.yaml](pvc.yaml), [configmap.yaml](configmap.yaml), [deployment.yaml](deployment.yaml), [service.yaml](service.yaml), [ingress.yaml](ingress.yaml): the pod and everything it needs.
- [deployer-system-networkpolicy.yaml](deployer-system-networkpolicy.yaml), [deployer-system-cilium-networkpolicy.yaml](deployer-system-cilium-networkpolicy.yaml): the fence around this namespace itself, in two kinds. Ingress only.
- [builds-namespace.yaml](builds-namespace.yaml), [builds-networkpolicy.yaml](builds-networkpolicy.yaml): the build namespace and the fence around it.
- [hello-world.yaml](hello-world.yaml): a hand applied app in the exact shape the control plane will generate. Not part of the kustomization.
- [gitops/](gitops/): reference copies for the separate `k3sprox-gitops` repository. Nothing here applies them.

## Conventions

- `deployment.yaml` holds an image digest, and the `publish` job in [.github/workflows/ci.yml](../.github/workflows/ci.yml) rewrites that line on every push to `main`. Do not hand edit the digest, and never put a `ko://` reference or a mutable tag there: ArgoCD applies this file verbatim, so it must always hold something a kubelet can pull.
- `replicas: 1` plus `strategy: Recreate` in `deployment.yaml` is load bearing twice over. It keeps two writers off one SQLite file, and it is also what makes the stranded deployment check in `internal/reconcile` correct: that check ends a deployment left sitting in `building` on the reasoning that a row observed there at the top of a tick cannot be one anybody is driving, which is only true while there is exactly one control plane pod. Raising the replica count would let it end deployments another pod is actively driving, so it is a decision that touches [spec 0014](../docs/specs/0014-stranded-deployment-recovery/index.md) rather than a scaling knob.
- The two cluster wide rights in `rbac.yaml` (namespaces, rolebindings) are fenced by `admission-policy.yaml`, because RBAC has no way to say "only namespaces named `app-*`". Widening one without checking the other reopens the escalation the pair exists to close. Everything the control plane does inside an app namespace belongs in `ClusterRole/deployer-app`, which is never bound cluster wide.
- The `AppProject` in `gitops/argocd-application.yaml` is scoped to the platform namespaces this repo owns and nothing else. That scope is what stops a sync with `prune: true` from reaching an `app-<slug>` namespace created at runtime, so it is load bearing, not boilerplate. Adding a namespace to this directory therefore means adding a destination there too, in the separate `k3sprox-gitops` repository (`apps/deployer.yaml`); the file here is a mirror that applies nothing. Forgetting it does not fail the one object: ArgoCD validates the whole operation, so an unlisted destination stops everything in `deploy/` from applying, and the app sits `OutOfSync` while looking healthy.
- Apps are served on the shared wildcard certificate through the `nginx` ingress class, so an app Ingress carries no `tls` block and no app namespace ever holds a private key. The `tailscale` class is for the control plane's own Ingress only.
- The console reaches the control plane through the Cloudflare tunnel and **not** through `ingress-nginx`, which is the opposite of how apps get there and is easy to assume the other way round (spec 0021). `cloudflared-configmap.yaml` routes the app wildcard to the nginx controller over verified HTTPS and routes `DEPLOYER_CONSOLE_HOST` straight to the `deployer` Service on 8080 over plain HTTP. That direct origin is load bearing rather than a shortcut: it is what lets `deployer-system-networkpolicy.yaml` name `deployer-edge` as the only outside peer on 8080, and therefore what lets the platform believe `CF-Connecting-IP` on the console hostname. Putting the console behind the shared controller, or adding `ingress-nginx` as a peer of `deployer-system`, makes that header writable from most of the cluster; a parse test in [internal/config](../internal/config) fails on the second of those and nothing catches the first.
- The tunnel routes exactly three hostnames and then refuses, so what is public is a reviewable file rather than a dashboard setting. The routing `ConfigMap`, the three hostnames, their distinct origins, the catch all, and the tunnel namespace's own two way policy are all pinned by `tunnel_test.go` in `internal/config`, which also pairs the console route against `DEPLOYER_CONSOLE_HOST` in `configmap.yaml`: those two live in different files, and a mismatch is a console that answers 404 through the tunnel while every other test passes.
- The third hostname is `DEPLOYER_MCP_HOST`, the deploy path, added by spec 0022 and pointed straight at the `deployer` Service exactly like the console. It **adds no network policy peer**: a second public name landing on a Service that already permits `deployer-edge` on 8080 needs nothing new, and a test asserts that rather than the build assuming it (AC-22). If you ever find yourself adding a peer to `deployer-system-networkpolicy.yaml` to make a public hostname work, the hostname is going somewhere it should not.
- The **order** of the tunnel's ingress rules is load bearing, and it is the second distinct way to get that same 404. cloudflared reads the rules top to bottom and takes the first hostname that matches, and `*.deploy.toyintest.org` matches `console.deploy.toyintest.org`, because a leading `*.` matches exactly one label. So the console rule goes above the wildcard, most specific first. With the wildcard first the console rule is unreachable and every console request is handed to `ingress-nginx`, which has no server block for that name and answers its own 404, while the app wildcard keeps working perfectly, so it reads as a console fault rather than a routing one. That shipped once and survived the whole suite, because the assertions read the rules by position and the two wrong positions agreed with each other. `TestNoTunnelRuleIsShadowedByAnEarlierOne` now walks every rule against the ones before it, and the other assertions look rules up by shape rather than by index. Nothing catches this before the tunnel is real: a `Host` header override aimed straight at the Service skips rule matching entirely. `cloudflared`'s image is pinned by digest and is the one image here CI does not rewrite, so bumping it means reading a digest off the registry by hand, along with the uid its OCI `User` field declares.
- This repository's tunnel is the **second** tunnel on the cluster and lives in `deployer-edge`, not in `cloudflared`. That namespace is already taken by a remotely managed tunnel owned by the `k3sprox-gitops` repository, carrying the dashboard held routes for every other app here. Two ArgoCD applications naming one `Deployment` is a fight, and the loser is the connector those apps run on, so the namespace name is load bearing rather than cosmetic. It also has to be listed as a destination on the `deployer` AppProject in `k3sprox-gitops` (`apps/deployer.yaml`), mirrored in `gitops/argocd-application.yaml`: an unlisted destination fails the whole sync, not just the tunnel.
- A deployed app learns the visitor's address from `CF-Connecting-IP`, and **not** from `X-Forwarded-For`, which on the public path names the tunnel rather than the visitor. `ingress-nginx` sets `X-Forwarded-For` and `X-Real-Ip` to its own immediate peer, and through the tunnel that peer is the `cloudflared` pod, so every public request looks like one `10.42.x` address. Measured 2026-08-16: the same app read `CF-Connecting-IP: <the real visitor>` while `X-Forwarded-For: 10.42.2.29`, and reading it directly on the LAN instead gave `X-Forwarded-For: <the LAN client>`, which is the same rule producing a different answer. The fix would be `use-forwarded-headers`, and it is deliberately unset because it is controller wide and would change behaviour for the twelve other apps on the shared controller. An app doing its own per visitor rate limiting on `X-Forwarded-For` would therefore put the whole internet in one bucket. No app manifest, no controller wide setting and no Go code changes for this. An app has **no** reason to trust either header: an app is reachable on the pod network as well as through the tunnel, so anything that reaches it can write both. They are documented here rather than rewritten, and an app that needs a trustworthy address needs its own reasoning about who can reach it.
- The registry Service's `clusterIP` in `registry.yaml` is pinned, and every node's `/etc/rancher/k3s/registries.yaml` mirrors the registry's `.svc` name to that address. It has to be an IP: containerd pulls images through the host resolver, which has no cluster DNS, so a `.svc` endpoint there fails every pull with "no such host". Changing the pinned address means editing all four nodes and restarting k3s on each.
- `DEPLOYER_BUILD_UID` and `DEPLOYER_BUILD_GID` belong to `DEPLOYER_BUILDER_IMAGE` and are repinned with it: they are the `CNB_USER_ID` and `CNB_GROUP_ID` that exact digest declares, and the build pod has to start as that user because the lifecycle under `restricted` holds no capability to switch to it. Nothing reads them off the image at run time, since that would put a Docker Hub call on the pod's startup path, so the `builder uid` step in [.github/workflows/ci.yml](../.github/workflows/ci.yml) reads them off the pinned digest and fails when they drift. Bumping the builder alone passes every unit test and kills every real build.
- `DEPLOYER_BUILDKIT_UID` and `DEPLOYER_BUILDKIT_GID` are the same idea for `DEPLOYER_BUILDKIT_IMAGE`, but BuildKit follows no `CNB_` convention, so the same `builder uid` step reads them off that image's OCI `Config.User`. That field is only required to carry a uid, and a uid alone answers both a `%%:*` and a `##*:` strip, so the step refuses anything that is not a `uid:gid` pair rather than comparing the gid against the uid and passing.
- `builds-networkpolicy.yaml` and `builds-dockerfile-networkpolicy.yaml` are applied by ArgoCD and never composed in Go, so nothing at run time would notice a hand edit that opens them up. Go tests in [internal/config](../internal/config) parse the files instead and pin their whole shape: deny both directions, no ingress rule on either policy, egress limited to CoreDNS and `deployer-system` on TCP 5000 and 8080, public egress limited to TCP 80 and 443, and an `except` list that must equal the `DEPLOYER_APP_EGRESS_BLOCKED_CIDRS` default in `isolation.go`. Widening any of that fails the suite, and the blocked range list has to be edited in both places at once. The build namespaces state the port bound the opposite way round from an app namespace: an allow list of two ports here, the complement of `DEPLOYER_APP_EGRESS_BLOCKED_PORTS` there, so neither restates the other.
- `deployer-system` is fenced by two objects of two different kinds, and you have to read both to know who reaches it (spec 0019). `deployer-system-networkpolicy.yaml` is a `networking.k8s.io/v1` pair carrying the pod sourced callers: the tailnet proxy, the two build namespaces, and the control plane pod itself, which is a peer of its own namespace because it reads a pushed image back from the registry over the pod network. `deployer-system-cilium-networkpolicy.yaml` is a `cilium.io/v2` object carrying the node sourced ones as the reserved `host` and `remote-node` identities. Node addresses cannot do that job: Cilium settles node traffic onto those identities before any CIDR rule is read, so four `/32` entries parsed clean, passed the shape test, and admitted nothing, and the only instrument that found it was an image pull on a node that is not the registry's. Both files are pinned by parse tests in [internal/config](../internal/config) the same way the build policies are, one kind per test file, and neither test can tell you a peer is missing, since a shorter list is a valid policy. Two things to keep: the Cilium object is the first thing in this directory that is not portable to another CNI, and it must stay namespaced, because the `deployer` AppProject's `clusterResourceWhitelist` does not name `cilium.io` and a cluster scoped version would stop everything here from applying while the app still read as healthy.
- `web-sealedsecret.yaml` carries `DEPLOYER_CSRF_KEY`, the key every page form's CSRF token is derived under, and it is the one Secret the pod refuses to start without. Sealing needs the cluster's own public key, so the file in the repo is a placeholder until it is produced against the cluster it will run on: `kubectl create secret generic deployer-web --from-literal=DEPLOYER_CSRF_KEY="$(openssl rand -hex 32)" --dry-run=client -o yaml | kubeseal -o yaml > deploy/web-sealedsecret.yaml`. Not optional on purpose, unlike the mail and bootstrap Secrets: a page surface that cannot verify its own forms should not serve them. Rotating it invalidates only the forms open at that moment, and a resubmit succeeds.
- The `deployer-backup` Secret holds the R2 access key pair and is sealed by hand against the cluster, the same way `deployer-web` is. Its `secretRef` in `deployment.yaml` is marked `optional: true`, and that flag means only that the reference resolves on a cluster nobody has given the pair to yet. It does not make backups optional one value at a time: the six `DEPLOYER_BACKUP_*` values are one all or nothing group, the other five sit in `configmap.yaml` (the age recipient included, since a recipient is a public key), and a cluster carrying those five without this pair refuses to start. Turning backups off means removing all six, not deleting this Secret.
- Every `DEPLOYER_*` value here has a matching validation in [internal/config](../internal/config/config.go). Adding a key to `configmap.yaml` without adding it there means the pod reads nothing; adding it there without adding it here fails the boot.
