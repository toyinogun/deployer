# deploy

The Kubernetes manifests for the control plane, applied by ArgoCD into `deployer-system`. Governing spec: [docs/specs/0003-cluster-foundation/index.md](../docs/specs/0003-cluster-foundation/index.md). File by file detail, the first apply steps, and the hand run checks live in [README.md](README.md).

## Layout

- [kustomization.yaml](kustomization.yaml): the apply order. A new manifest is invisible to ArgoCD until it is listed here.
- [namespace.yaml](namespace.yaml), [rbac.yaml](rbac.yaml), [admission-policy.yaml](admission-policy.yaml): the namespace, the service account rights, and the fence around them.
- [pvc.yaml](pvc.yaml), [configmap.yaml](configmap.yaml), [deployment.yaml](deployment.yaml), [service.yaml](service.yaml), [ingress.yaml](ingress.yaml): the pod and everything it needs.
- [builds-namespace.yaml](builds-namespace.yaml), [builds-networkpolicy.yaml](builds-networkpolicy.yaml): the build namespace and the fence around it.
- [hello-world.yaml](hello-world.yaml): a hand applied app in the exact shape the control plane will generate. Not part of the kustomization.
- [gitops/](gitops/): reference copies for the separate `k3sprox-gitops` repository. Nothing here applies them.

## Conventions

- `deployment.yaml` holds an image digest, and the `publish` job in [.github/workflows/ci.yml](../.github/workflows/ci.yml) rewrites that line on every push to `main`. Do not hand edit the digest, and never put a `ko://` reference or a mutable tag there: ArgoCD applies this file verbatim, so it must always hold something a kubelet can pull.
- `replicas: 1` plus `strategy: Recreate` in `deployment.yaml` is load bearing twice over. It keeps two writers off one SQLite file, and it is also what makes the stranded deployment check in `internal/reconcile` correct: that check ends a deployment left sitting in `building` on the reasoning that a row observed there at the top of a tick cannot be one anybody is driving, which is only true while there is exactly one control plane pod. Raising the replica count would let it end deployments another pod is actively driving, so it is a decision that touches [spec 0014](../docs/specs/0014-stranded-deployment-recovery/index.md) rather than a scaling knob.
- The two cluster wide rights in `rbac.yaml` (namespaces, rolebindings) are fenced by `admission-policy.yaml`, because RBAC has no way to say "only namespaces named `app-*`". Widening one without checking the other reopens the escalation the pair exists to close. Everything the control plane does inside an app namespace belongs in `ClusterRole/deployer-app`, which is never bound cluster wide.
- The `AppProject` in `gitops/argocd-application.yaml` is scoped to the platform namespaces this repo owns and nothing else. That scope is what stops a sync with `prune: true` from reaching an `app-<slug>` namespace created at runtime, so it is load bearing, not boilerplate. Adding a namespace to this directory therefore means adding a destination there too, in the separate `k3sprox-gitops` repository (`apps/deployer.yaml`); the file here is a mirror that applies nothing. Forgetting it does not fail the one object: ArgoCD validates the whole operation, so an unlisted destination stops everything in `deploy/` from applying, and the app sits `OutOfSync` while looking healthy.
- Apps are served on the shared wildcard certificate through the `nginx` ingress class, so an app Ingress carries no `tls` block and no app namespace ever holds a private key. The `tailscale` class is for the control plane's own Ingress only.
- The registry Service's `clusterIP` in `registry.yaml` is pinned, and every node's `/etc/rancher/k3s/registries.yaml` mirrors the registry's `.svc` name to that address. It has to be an IP: containerd pulls images through the host resolver, which has no cluster DNS, so a `.svc` endpoint there fails every pull with "no such host". Changing the pinned address means editing all four nodes and restarting k3s on each.
- `DEPLOYER_BUILD_UID` and `DEPLOYER_BUILD_GID` belong to `DEPLOYER_BUILDER_IMAGE` and are repinned with it: they are the `CNB_USER_ID` and `CNB_GROUP_ID` that exact digest declares, and the build pod has to start as that user because the lifecycle under `restricted` holds no capability to switch to it. Nothing reads them off the image at run time, since that would put a Docker Hub call on the pod's startup path, so the `builder uid` step in [.github/workflows/ci.yml](../.github/workflows/ci.yml) reads them off the pinned digest and fails when they drift. Bumping the builder alone passes every unit test and kills every real build.
- `DEPLOYER_BUILDKIT_UID` and `DEPLOYER_BUILDKIT_GID` are the same idea for `DEPLOYER_BUILDKIT_IMAGE`, but BuildKit follows no `CNB_` convention, so the same `builder uid` step reads them off that image's OCI `Config.User`. That field is only required to carry a uid, and a uid alone answers both a `%%:*` and a `##*:` strip, so the step refuses anything that is not a `uid:gid` pair rather than comparing the gid against the uid and passing.
- `builds-networkpolicy.yaml` is applied by ArgoCD and never composed in Go, so nothing at run time would notice a hand edit that opens it up. Go tests in [internal/config](../internal/config) parse the file instead and pin its whole shape: deny both directions, no ingress rule on either policy, egress limited to CoreDNS and `deployer-system` on TCP 5000 and 8080, and an `except` list that must equal the `DEPLOYER_APP_EGRESS_BLOCKED_CIDRS` default in `isolation.go`. Widening any of that fails the suite, and the blocked range list has to be edited in both places at once.
- `web-sealedsecret.yaml` carries `DEPLOYER_CSRF_KEY`, the key every page form's CSRF token is derived under, and it is the one Secret the pod refuses to start without. Sealing needs the cluster's own public key, so the file in the repo is a placeholder until it is produced against the cluster it will run on: `kubectl create secret generic deployer-web --from-literal=DEPLOYER_CSRF_KEY="$(openssl rand -hex 32)" --dry-run=client -o yaml | kubeseal -o yaml > deploy/web-sealedsecret.yaml`. Not optional on purpose, unlike the mail and bootstrap Secrets: a page surface that cannot verify its own forms should not serve them. Rotating it invalidates only the forms open at that moment, and a resubmit succeeds.
- Every `DEPLOYER_*` value here has a matching validation in [internal/config](../internal/config/config.go). Adding a key to `configmap.yaml` without adding it there means the pod reads nothing; adding it there without adding it here fails the boot.
