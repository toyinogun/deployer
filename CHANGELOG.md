# Changelog

All notable changes to this project are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- First deploy end to end: an agent can upload a source tarball, call one MCP tool, and get back a working HTTPS hostname for the running app (see spec 0004).
- `deploy_app` MCP tool, taking `name` and `upload_id`. It builds the source with Cloud Native Buildpacks in a Kubernetes Job, pushes the image to the in cluster registry, composes the app's Deployment, Service and Ingress, waits for the app to answer, and returns the name, slug, URL and deployment id. The call does not wait for the build; `deployment_status` reports the outcome (see spec 0005 below).
- `POST /v1/uploads`, which accepts a gzipped tar body against a bearer token, rejects a body over `DEPLOYER_MAX_UPLOAD_BYTES` with 413 before writing it all to disk, records the size and SHA-256, and returns the upload id and its expiry.
- `GET /v1/uploads/{id}`, a single use redeem path used only by the build Job's init container to fetch the tarball.
- `fetch-source` subcommand, run as the build Job's init container. It verifies the recorded SHA-256 before unpacking and refuses any archive entry with an absolute path, a `..` component, a symlink, a hardlink or a device node, along with any archive over the file count or uncompressed size caps.
- Redeploying an app under the same name keeps the same hostname and increments the release number, so a link already handed to someone keeps working.
- A closed set of failure reason codes on every failed deploy (`upload_invalid`, `upload_expired`, `source_rejected`, `build_failed`, `build_no_digest`, `image_runs_as_root`, `app_never_ready`, `timeout`, `internal`), returned to the caller and stored on the deployment. Raw build output never reaches the response, the database, or the platform log at info level.
- A startup sweep that reconciles every non terminal deployment against the cluster, so a control plane restart during a build resumes a live Job and fails one that has vanished, rather than leaving a deployment stuck.
- An in cluster container registry (`distribution` v3) in `deployer-system`, backed by a Longhorn volume, with htpasswd auth held only as a `SealedSecret`, and no Ingress. Plus the `deployer-builds` namespace with `enforce: restricted` pod security.
- Bootstrap seeding at startup: when `DEPLOYER_BOOTSTRAP_TOKEN` is set, the platform ensures one `bootstrap` account and one token row holding that token's SHA-256 hash. Running it again changes nothing, and the raw token is never logged.
- New settings, all validated at startup so a missing or malformed one fails the boot naming the variable: `DEPLOYER_BOOTSTRAP_TOKEN`, `DEPLOYER_PUBLIC_URL`, `DEPLOYER_INTERNAL_URL`, `DEPLOYER_BUILDER_IMAGE`, `DEPLOYER_SELF_IMAGE`, `DEPLOYER_BUILD_UID`, `DEPLOYER_BUILD_GID`, `DEPLOYER_DEPLOY_TIMEOUT_SECONDS`, `DEPLOYER_BUILD_TIMEOUT_SECONDS`, `DEPLOYER_READY_TIMEOUT_SECONDS`, `DEPLOYER_RECONCILE_INTERVAL_SECONDS`, `DEPLOYER_APP_DEFAULT_CPU`, `DEPLOYER_APP_DEFAULT_MEMORY`, `DEPLOYER_APP_LIMIT_CPU`, `DEPLOYER_APP_LIMIT_MEMORY`, `DEPLOYER_MAX_UPLOAD_FILES`, `DEPLOYER_MAX_EXTRACTED_BYTES`.
- A CI step that reads the pinned builder image's own `CNB_USER_ID` and `CNB_GROUP_ID` and fails on drift from `DEPLOYER_BUILD_UID` and `DEPLOYER_BUILD_GID`.
- `testdata/sample-go`, a minimal sample app used to prove the whole path against the real cluster.
- Async deployment jobs and status: the deploy call stops waiting, so a client's request timeout has nothing to do with how long a build takes (see spec 0005).
- `deployment_status` MCP tool, taking exactly one of `deployment_id` or `name`. It reports the deployment's state and a timeline of every recorded transition, plus the release number and image digest once healthy, the reason code and its one line when failed, and `superseded` with the id that replaced it when cancelled. Polling it every few seconds is the intended shape, and its description says so.
- A watchdog inside the reconcile loop, which fails any deployment that runs past `DEPLOYER_DEPLOY_TIMEOUT_SECONDS` with reason `timeout` and deletes its build Job. Every deployment now ends by itself, which the blocking call used to cover by giving up.
- Two more failure reason codes, `deployment_unknown` and `superseded`, taking the closed set from nine to eleven. `superseded` describes a cancellation rather than a failure.
- A fetch of an upload whose tarball has already been deleted answers `410 Gone` in the same words as an expired upload, rather than an internal error. That path became reachable once the watchdog could delete a tarball while a build was still fetching it.
- Application logs: an agent can read back the output of an app it deployed, so a misbehaving app can be debugged without anyone opening a terminal (see spec 0006).
- `get_logs` MCP tool, taking an app `name` and an optional `tail_lines`. It returns the newest lines still on the node, oldest first, each with the timestamp the kubelet recorded. It is a snapshot, not a stream: no follow, no search, no time window. `tail_lines` defaults to 200 and is capped at 1000, and a larger ask is clamped rather than refused, with the response echoing the value applied. The answer is capped by size as well as by line count; when the size cap is hit the oldest lines go, never the newest, and `truncated` and `dropped` say so.
- An app that crashed and restarted gets a second, smaller block of the dead container's output in `previous`, capped independently of the current block so restart noise can never squeeze the crash out of the answer. It is absent when there has been no restart.
- Secrets are blanked before the lines are returned, on a best effort basis the tool description states plainly: bearer and basic credentials, JWTs, passwords inside URLs, AWS style access key ids, and assignments named like a key, token, secret, or password. The registry credential the platform placed in the app's namespace is matched exactly, because that is the one value the platform knows for certain is secret. High entropy alone is deliberately not a trigger, because blanking on it destroys ordinary output.
- An app with no container started yet is a success with no entries, carrying the deployment's current state and one sentence saying why there is nothing to show. That is what every read during a build sees, and it now reads the same way whether the app's namespace is missing or merely not readable by the platform yet.
- One more reason code, `app_unknown`, taking the closed set from eleven to twelve. A log read for a name that does not exist and one for an app belonging to another account get the same answer, so the tool cannot be used to learn which app names exist. Only a refusal is audited; a successful read is not an access decision.
- No new settings. The log bounds are constants, because they are decisions about what fits an agent's context window rather than per deployment tuning, and nothing about a log read is stored: the platform reads from Kubernetes at the moment of the call and hands the lines back.
- Accounts, API tokens and app ownership: the platform stops having exactly one credential seeded from an environment variable. A person registers with an email and a password, verifies the address by clicking a link, signs in to a browser session, and mints API tokens from there for their coding agent to carry (see spec 0007). No pages are built yet: every endpoint is JSON and drivable with curl, and the web interface is its own later feature.
- Registration and verification endpoints: `POST /v1/auth/register`, which stores the password as an argon2id hash and issues a single use link valid for 24 hours, `GET /v1/auth/verify`, which consumes the link exactly once, and `POST /v1/auth/resend`, which supersedes the previous link so at most one is ever live. A password must be at least 12 characters and no other composition rule is applied. The first account created with an email becomes the admin; the bootstrap account has no email, so it never counts as the first and can never be signed into.
- Password reset: `POST /v1/auth/forgot`, which answers the same whether the address exists or not, and `POST /v1/auth/reset`, which sets the new hash, consumes the link, and revokes every live session for that account. Verification links and reset links share one table and are matched on their hash and their purpose together, never on the hash alone, so a link of one kind presented as the other is refused.
- Sessions: `POST /v1/auth/login` sets an opaque session id in a cookie marked `HttpOnly` and `SameSite=Lax`, and `Secure` when `DEPLOYER_PUBLIC_URL` is an https URL. A session expires 30 days after its last use and each authenticated request pushes that forward. `POST /v1/auth/logout` revokes it immediately.
- Token endpoints: `POST /v1/tokens` mints a token and returns the raw value exactly once, storing only its SHA-256 hash and its 8 character prefix, with an optional lifetime between 1 and 365 days. `GET /v1/tokens` lists the caller's live tokens with no raw value and no hash, and `DELETE /v1/tokens/{id}` revokes one, which stops authenticating on the very next request.
- Admin endpoints, session only and admin only: `GET /v1/admin/accounts`, `POST /v1/admin/accounts/{id}/disable` and `/enable`, and `DELETE /v1/admin/accounts/{id}/tokens/{tokenId}`. An API token presented to an admin endpoint is refused, because admin surfaces accept sessions alone.
- Migration `00002_identity.sql`: five columns on `accounts` (`email`, `password_hash`, `email_verified_at`, `is_admin`, `display_name`) plus the `sessions` and `email_tokens` tables. `display_name` is a new column rather than a reuse of `accounts.name`, which is unique and was designed as a machine identifier, so two people at `info@a.example` and `info@b.example` would otherwise collide on a constraint with no sensible error to return.
- Verification and reset mail goes out through Resend, behind two new settings validated at startup like every other one: `DEPLOYER_RESEND_API_KEY` and `DEPLOYER_MAIL_FROM`. With the key unset, register, resend and password reset answer `503 mail_unavailable` while every other endpoint, and the whole MCP and upload path, works normally.
- Workload isolation and network policy: an app an agent deployed can no longer reach your other apps or your cluster services (see spec 0008). Every app namespace gets two NetworkPolicy objects composed field by field in Go, `default-deny` which selects every pod and carries no rules in either direction, and `app-allow` which permits back exactly three things.
- The three allows are narrow on purpose: inbound only from the `ingress-nginx` namespace on TCP 8080, outbound only to the CoreDNS pods in `kube-system` on UDP and TCP 53, and outbound to `0.0.0.0/0` with every configured private range carved out under `except`. The DNS rule pairs its namespace selector and pod selector inside one peer, so it means the CoreDNS pods in kube-system rather than anything in kube-system or anything labelled kube-dns anywhere. Getting that wrong opens the whole namespace.
- A startup policy sweep walks every namespace the platform manages and applies both policies, so app namespaces created before this slice are fenced without being redeployed. It runs before the existing deployment sweep, and a failure on one namespace is logged and does not stop the rest.
- The `deployer-builds` namespace gets an equivalent fixed pair delivered as static YAML under GitOps, because a build pod runs an AI written project's dependency install beside a registry push credential. It drops the ingress rule entirely, since nothing connects to a build pod, and adds one egress peer for the registry and the platform API the build pod fetches source from.
- One new setting, `DEPLOYER_APP_EGRESS_BLOCKED_CIDRS`, the comma separated ranges an app and a build pod may not reach. It defaults to the pod range, the service range, the nodes and LAN, link local and cloud metadata, and the Tailscale range. Unset or empty falls back to that default, because a ConfigMap that omits the key has to boot fenced rather than open, and a value that is set but leaves no usable entry stops the process at boot rather than silently turning the fence into an open door.
- `testdata/probe`, a probe app that reports over HTTP the outcome of a dial against a sibling pod IP, a sibling Service IP, the Kubernetes API, the registry, a node IP, the ingress load balancer and a public host. It is deployed twice under two slugs so each instance is the other's sibling, and every dial carries a timeout, because a blocked destination is a silent drop rather than a refusal and an untimed dial hangs forever.
- Dockerfile build path: when an uploaded project ships a `Dockerfile` at its root, the platform builds that instead of running Buildpack detection, so an app Buildpacks cannot handle still deploys (see spec 0009). A project without one is unaffected and still builds through Buildpacks with no observable change.
- The path is chosen on the control plane, by walking the stored archive's tar entry names before the build Job is composed, because a Job's container image is fixed the moment it is created. The walk reads headers only and never bodies, never extracts to the control plane's own filesystem, and is bounded by the same file count limit the extractor enforces. Only a regular file entry counts: a directory or link entry whose name cleans to `Dockerfile` does not select the Dockerfile path.
- `deployments.build_path` is written as `dockerfile` or `buildpacks` at the moment the path is chosen, before the Job exists, so a deployment that fails still reports which engine ran. `deployment_status` reports it for any deployment that reached `building` or beyond and omits it before that.
- The Dockerfile build is one rootless BuildKit container running `buildctl-daemonless.sh` from a digest pinned image, pushing straight to the in cluster registry, with no cache export, no build arguments, no secrets and no entitlements granted.
- A second build namespace, `deployer-builds-dockerfile`, enforcing `privileged` and holding BuildKit Jobs and nothing else. `deployer-builds` goes back to enforcing `restricted` for Paketo. `baseline` was tried on the cluster first and refuses the BuildKit pod outright, because it forbids two of the four deviations that pod needs. Both namespaces carry the same NetworkPolicy pair and the same control plane RoleBinding, and a test pins both files so the second cannot drift open on its own.
- Four new settings, all validated at startup: `DEPLOYER_BUILDKIT_IMAGE`, `DEPLOYER_BUILDKIT_UID`, `DEPLOYER_BUILDKIT_GID` and `DEPLOYER_BUILDKIT_NAMESPACE`, plus `DEPLOYER_BUILD_NAMESPACE` for the Paketo side. The two namespaces are refused if they are equal, since one namespace cannot enforce both levels. CI now reads both pinned build images' declared users and fails when either drifts from the pair configured for it.
- `testdata/sample-dockerfile`, a sample app that deploys through the Dockerfile path, so one verify run proves both engines against the real cluster.
- App environment configuration: an app can be given the values it was written against, so anything needing an API key or a database address is deployable here at all (see spec 0010).
- `set_config` MCP tool, taking an app `name` and a `config` map of key to `{value, secret}`. It merges the keys into whatever is already set, in one transaction, and returns the resulting configuration. Every key needs its `secret` flag; a key sent without one is refused with `config_flag_missing`, so re setting an existing key can never quietly turn a secret into a plain value.
- `unset_config` MCP tool, taking an app `name` and a list of `keys`. It removes them in one transaction. If any key in the call is not set, the whole call is refused with `config_key_unknown` and nothing is removed.
- `get_config` MCP tool, listing every key with its secret flag, and its value only when the key is not secret.
- `deploy_app` gains an optional `config` map of the same shape, validated by exactly the same rules and written before the deployment row is created, so a brand new app's first run is not a guaranteed crash on a missing variable. A call carrying no map leaves the configuration untouched.
- A deploy composes one Kubernetes Secret named `config` in the app's namespace holding every configured key and value, and the container receives them with `envFrom`. The values are read once, when the workload is composed, so a change landing mid build reaches that same deploy and nothing later moves under it.
- `APP_URL` is injected beside `PORT`, built from the same host the Ingress rule takes, so an app can build a link to itself on its first run. Both are composed by the platform and neither can be stored: `PORT` and `APP_URL` are refused with `config_key_reserved`.
- The pod template carries an annotation holding a checksum of the configuration it was composed with, so a deploy whose image digest is unchanged still rolls the pods and the new values actually reach the container.
- Configuration is bounded: 64 keys for one app, 4 KB for one value, 32 KB for the whole set, refused with `config_too_many_keys` and `config_too_large`. A key must match `[A-Z_][A-Z0-9_]*` or it is refused with `config_key_invalid` before any write, so the database constraint is a backstop rather than the error reporter. An empty string is a valid value and is not the same thing as the key being unset.
- Six more reason codes, `config_key_invalid`, `config_key_reserved`, `config_key_unknown`, `config_flag_missing`, `config_too_many_keys` and `config_too_large`, taking the closed set from twelve to eighteen. Every one of them is decided before any write, so a refused call changes nothing.
- No new settings and no migration. The bounds are Go constants, because they are decisions about what an app should carry rather than knobs for whoever runs the platform, and the `app_config` table and the release's `config_snapshot` column were designed for this back in spec 0002.
- `testdata/envprint`, a sample app that prints its own environment, used to prove the values reach a real container.
- Rollback and release history: an agent can list an app's known good releases and go back to one, so recovering from a bad deploy does not mean waiting out another build (see spec 0011).
- `list_releases` MCP tool, taking an app `name` and returning that app's newest twenty releases, newest first, each with its release number, image digest, creation time, deployment id, and whether it is the one currently serving. There is no caller supplied limit and no cursor, and its description says older releases are not reachable through MCP.
- `rollback_app` MCP tool, taking an app `name` and a required `release_number`. It writes a queued rollback and returns straight away without waiting for the rollout. A release number that does not exist for that app is refused with `release_unknown` and nothing is written. Rolling back to the release already current is not refused: it re promotes the same digest and rewrites the configuration from the snapshot.
- A rollback restores the whole app, not just the image. It composes the configuration Secret and the pod template checksum from the source release's snapshot rather than from current configuration, and the checksum change is what rolls the pods when the image digest has not moved. On success `app_config` is rewritten to exactly the snapshot's keys inside the same transaction that marks the deployment healthy, so `get_config` afterwards agrees with what is running.
- The reconcile loop learned what kind of deployment it is driving. A rollback goes from `queued` straight to `deploying`: no build Job, no fetch token, no upload read, no registry digest resolution. The deployment carries its source release, so a control plane restart picks a rollback back up as a rollback rather than failing it as a build deploy with a missing upload.
- One more reason code, `release_unknown`, taking the closed set from eighteen to nineteen.
- A release's configuration snapshot now records a secret flag per key rather than a bare value, on every deploy and not only on a rollback, because a snapshot written without the flag has nothing to restore the flag from. Reading accepts both shapes, decided per key, with no migration and no schema change.
- No new settings. A rollback runs under the same deploy budget as a build deploy.
- App lifecycle, list and decommission: an agent can see what it has deployed and tear an app down cleanly, which matters most when it is generating throwaway apps (see spec 0012).
- `list_apps` MCP tool, taking no arguments at all: the account comes from the token and the bound is the platform's. Each app reports its name, slug, url and creation time, plus two separate facts that reading as one is the mistake the listing exists to prevent. `serving` is the release the app is running right now, and `last_deployment` is how the most recent deploy ended. An app whose last deploy failed is usually still serving its previous release, so a row carrying both a serving release and a failed last deployment means the app is up and the new version is not. An app never healthy has no `serving` object, one never deployed has no `last_deployment` object, and a deploy still running appears with its live state. It returns at most the newest 50 apps and there is no way to page past them, which its description says plainly.
- `delete_app` MCP tool, taking an app `name`. One Kubernetes call deletes the app's whole namespace, which cascades the Deployment, Service, Ingress, Secret, both NetworkPolicies, the ResourceQuota, the LimitRange and the RoleBinding together. Nothing is deleted object by object. The call does not wait for the cluster to finish terminating, and returns once the delete is recorded and issued.
- An orphan namespace reaper, the platform's first unattended destructive loop. It runs on its own ticker and once at startup, and deletes every app namespace the platform owns whose slug matches no live app row. Every guard on it is load bearing: only namespaces carrying both of the platform's labels are considered at all, a namespace younger than the grace is out of reach, and a live slug read that fails aborts the whole pass rather than reading as nothing owning anything. One namespace that will not delete is logged and stepped over so the rest of the pass still runs.
- One more reason code, `deployment_in_flight`, taking the closed set from nineteen to twenty. A delete of an app with a deploy or rollback still running is refused whole: nothing is written and nothing is torn down, because tearing the namespace down now would pull it out from under a build writing into it.
- Two new settings, both validated at startup like every other one: `DEPLOYER_REAP_INTERVAL_SECONDS`, how often the reaper runs, ten minutes by default, and `DEPLOYER_ORPHAN_GRACE_SECONDS`, how old a namespace must be before a pass may consider it, fifteen minutes by default. Neither has any required relationship to the deploy timeout, because an app's row is live for the whole of every build and so an app mid deploy is never a candidate whatever these are set to.
- Web interface: a browser surface over everything the platform already holds, so a person can see their apps, releases, output and tokens without curl and without asking their agent (see spec 0013). Pages are rendered server side by the deployer binary from `html/template`, with the templates, one stylesheet and one script embedded with `go:embed`. No node toolchain enters the repo, `ko build` is unchanged, and the image gains no layer beyond the binary.
- The whole identity flow is drivable in a browser: `/register`, `/verify`, the unverified page with its resend, `/forgot`, `/reset`, `/login` and `POST /logout`. Verification and reset mail now links to these pages rather than to `/v1/auth/…`. A duplicate registration renders the identical check your email page a fresh one does, and a consumed, expired, unknown or wrong purpose link renders one shared link invalid page in the same words for all four.
- App pages, read only on purpose: `/apps` lists the account's apps twenty at a time over the existing keyset cursor with a **Load more** control, `/apps/{slug}` shows the app with its serving release and its last deployment, `/apps/{slug}/releases` pages the release history marking the one currently serving, `/apps/{slug}/logs` renders the app's recent output in a dark pane read from Kubernetes at the moment of the request, and `/apps/{slug}/config` lists every key with its secret flag. Every action that changes an app stays with the agent over MCP; there is no deploy, rollback or delete button.
- Serving and last deploy stay two independent facts on every page, as spec 0012 defined them. An app whose newest deploy failed shows both the release it is still serving and the failure, because reading the serving release off the latest deployment answers not found exactly when the page matters most.
- A deployment that did not succeed shows one plain sentence written for its closed reason code, with the raw code small beside it, and `superseded` renders as cancelled rather than as a failure. A code with no sentence renders the raw code rather than an empty element.
- While a deployment is still running, the embedded script re fetches `GET /apps/{slug}?partial=status` every three seconds and swaps only the status region. It stops on a terminal state, stops after fifteen minutes regardless, and stops silently when a poll answers with anything but success, so a session that expired underneath the page leaves it as it stands rather than breaking visibly.
- `/tokens` lists the account's live tokens with name, eight character prefix, created, last used and expiry, mints one into a one time panel with a copy control and a warning that it will not be shown again, and revokes one. `/admin/accounts`, session only and admin only, lists every account and carries disable, enable and foreign token revoke, with disable behind typing the target's email address.
- A verified account with no apps yet sees an onboarding panel rather than an empty list: the MCP endpoint, the upload endpoint, and a link to mint a token. Every list surface has a written empty state distinguishable from something being broken.
- One design system, embedded as a single stylesheet: a deep green accent on a neutral shell, one radius, type and spacing scale, a left sidebar beside an inset content panel, cross document View Transitions with a staggered list entrance, everything disabled under `prefers-reduced-motion: reduce`, and every page usable down to a 375px viewport where the sidebar collapses and tables reflow to stacked cards. Every colour is a custom property even though the feature is light theme only, so dark mode later is a token swap. With JavaScript off every page renders and every form submits; only live polling, copy to clipboard and the collapsing sidebar are lost.
- One new setting, `DEPLOYER_CSRF_KEY`, validated at startup like every other one and refused under 32 bytes. It is required rather than generated at boot, because a generated key would differ per pod and would invalidate every open form on a restart. It ships as a `SealedSecret` in `deploy/`, whose sealed value is still a placeholder: sealing needs the cluster's own public key, so it has to be produced against the cluster with `kubeseal`, and the control plane will not start until it is.
- One new sqlc query and no schema change, `ListAppSummaryPage`: the existing app summary projection with the keyset cursor the app listing already carries, because the apps page needs the serving release and the last deploy state on a page that also pages, and neither existing query had both.
- A package test suite for `internal/web` covering every acceptance criterion through a real server: routing and the session gate, the CSRF and origin refusals, the failure reason sentences, the paging controls, the reveal route, admin access, and a crawl asserting no page body or log line carries a session id, a raw token or a secret value.
- A check at the top of each reconcile tick that asks the cluster what a `building` deployment's build Job actually did, and then either ends the row with the reason that answer justifies or hands it back to be resumed (see spec 0014). Be clear how narrow it is: a control plane restart is already resolved by the startup sweep, and a build Job that dies while the process is up by the poll already watching it. What is left, and what this exists for, is the pair of faults where a row sits in `building` with genuinely nothing driving it: a state write that did not land, and a startup sweep whose listing failed. Both were silent, and both cost a full deploy budget. It adds no setting, no migration, and no second writer of deployment state.
- Bounded app egress: a deployed app can no longer open outbound mail straight to a mail exchanger on port 25, or the stratum ports mining pools most often listen on (see spec 0017). Ordinary outbound HTTP and HTTPS still work, and so does a mail provider's relay on 587, so an app that legitimately sends mail has a path that does not run through port 25. Ports rather than hostnames, on purpose: an allow list by hostname would break every app that calls an API until its owner declared it.
- One new setting, `DEPLOYER_APP_EGRESS_BLOCKED_PORTS`, the comma separated TCP ports an app may not reach on any public address, validated at startup like every other one. It defaults to `25,3333,4444,5555,7777,9999,14444`. The boot fails naming the variable when an entry is not a usable port number, when the list leaves no port blocked at all, and when it covers the whole port space and would leave an app no outbound TCP whatsoever. Both of those refusals are a silent inversion of the rule rather than a broken one, which is why they stop the process rather than being logged.
- The blocked list is never what a policy carries. A NetworkPolicy can only permit a port, never refuse one, so `internal/deploy` complements the list over 1..65535 and the app's public egress rule carries those ranges: a blocked port is one that appears in no range. The ranges are never written as literals anywhere, so the configured list stays the single description of what an app may reach.
- `testdata/probe` gains three named public targets, `public_smtp_mx`, `public_stratum` and `public_smtp_relay`, joining the existing `public_host` on 443 to make the four the bound is read from on a live cluster. Each is a host that genuinely listens on that port, because a target with nothing listening reads as refused whatever the policy says and could never tell a bound apart from an absent listener.
- Platform backup and restore: the control plane copies its own database out of the cluster once a day, encrypted to a key the cluster does not hold (see spec 0020). Until now one lost volume was every account, every app and every secret anyone ever set, because nothing copied the database anywhere at all.
- One run is a consistent snapshot taken with `VACUUM INTO` through the running process's own database handle, so nothing is quiesced and the platform keeps serving throughout. The snapshot is opened as a separate read only database and checked while it is still plaintext, `PRAGMA integrity_check` must return exactly `ok` and the `accounts` table must hold at least one row, then it is encrypted to the configured age recipient, uploaded to the bucket, and read back and compared on both byte length and SHA-256 before the run is recorded as succeeded. A read back that does not match fails the run and leaves the object in place, because a partly readable backup is worth more than none.
- The account count is what catches a snapshot that is structurally perfect and empty. `integrity_check` is perfectly happy with one of those, and it would restore to a platform nobody can sign in to.
- After encrypting, the age header of the finished file is read back and confirmed to carry the stanzas the configured recipient produced. An X25519 header names no recipient, so nothing without a private key can read a recipient out of one: what can be proved without a key is that the header on disk is the header this recipient made. It is the only check that catches encrypting to a key nobody holds, which otherwise produces a well formed object that passes every other check and decrypts for nobody.
- Migration `00004_backup_runs.sql`, one new `STRICT` table recording every run: when it started and finished, its outcome, the object key, the size and checksum, the failure reason where there is one, and whether the schedule or a person fired it. At most one run at a time is a partial unique index rather than a check in Go, the same way `deployments_one_in_flight` already works, and every ending update carries `AND outcome = 'running'` so a row something else already ended cannot be written over. Rows are never pruned, deliberately, matching how releases already accumulate.
- A closed set of backup failure reason codes, its own type separate from the deploy reasons: `snapshot_failed`, `integrity_failed`, `encrypt_failed`, `upload_failed`, `verify_failed`, `stranded` and `internal`. The wrapped error never reaches the row, the page, or the platform log at info level.
- A ticker fires a run every `DEPLOYER_BACKUP_INTERVAL_SECONDS`, measured from the end of each run so a tick never lands on the heels of one that just finished. At startup it runs one immediately only when the newest success is older than the interval, so a pod that restarts often still gets backed up without backing up on every restart. A tick arriving while a run is in flight skips with a log line rather than attempting an insert it knows the index will refuse.
- A startup sweep, before the process serves anything, ends any row a dead predecessor left running and empties the temporary directory. It runs whether or not backups are configured, because a platform someone switched them off on still has whatever a killed run left behind.
- A failed run mails `DEPLOYER_BACKUP_ALERT_EMAIL` once through the existing Resend path, and the first success after any failure mails once to say so. A success after a success mails nothing, so silence means healthy, and the very first run the platform ever takes has no predecessor and is never a recovery.
- Six new settings forming one all or nothing group, validated at startup like every other one: `DEPLOYER_BACKUP_AGE_RECIPIENT`, `DEPLOYER_BACKUP_S3_ENDPOINT`, `DEPLOYER_BACKUP_S3_BUCKET`, `DEPLOYER_BACKUP_S3_ACCESS_KEY_ID`, `DEPLOYER_BACKUP_S3_SECRET_ACCESS_KEY` and `DEPLOYER_BACKUP_ALERT_EMAIL`. Present them all and backups are on, present none and backups are off, present some and the process refuses to start. The alert address is inside the group on purpose, because backups configured with nowhere to complain to is the precise failure this feature exists to prevent. Two optional ones sit outside it, `DEPLOYER_BACKUP_INTERVAL_SECONDS` defaulting to 86400 and `DEPLOYER_BACKUP_S3_REGION` defaulting to `auto`.
- With none of it configured the platform boots, logs one warning naming exactly which values are missing, takes no backups, records no runs, and works in every other respect, the same way the Resend key and the bootstrap token already behave.
- `GET /admin/backups`, behind the same admin session gate every other admin page uses, listing the most recent runs with when each started and finished, its outcome, size, object key and reason. It renders a written not configured state when no bucket is set rather than an empty table that reads as healthy. The object key is shown because it is what you type into `deployer restore`; the bucket name and the credential are not there and never will be.
- `POST /admin/backups/run` fires a backup outside the schedule, carrying the same session bound CSRF token the other admin writes carry. A run refused because one is already going tells you so with the closed reason code and writes nothing beyond the audit row, and every press writes an audit row whether it was allowed or refused.
- `deployer restore`, a subcommand of the same binary meant to run outside the cluster. Given an object key, the bucket configuration and a path to an age identity file it fetches the object, decrypts it, runs the same integrity check the run made before uploading, and writes the plaintext database to a local path. It refuses a destination that already exists, and it restores to a file and nothing more: getting that file onto the volume is a documented step rather than something the subcommand does.
- A runbook in `deploy/README.md` covering the whole path end to end: scaling the control plane down, placing the restored file, scaling back up, and what to check afterwards. It also names the exact command for exporting the sealed secrets controller key by hand, and says to repeat it whenever the controller rotates.
- The registry volume is backed up to the same bucket by a Longhorn recurring job configured in the `k3sprox-gitops` repository, with a retention of 30. No Go code here touches it. It is listed so the feature is not called done with the images missing.
- The public edge: the console and every deployed app answer on the open internet, so joining the platform no longer starts with installing a VPN and a link to an app you built is a link someone can open (see spec 0021). A Cloudflare tunnel dials out from the cluster, so no port is opened on the router and no DNS record and no certificate carries a home address. The deploy path does not go with it: the MCP endpoint, the tarball upload and every admin page stay on the tailnet, because the surface that runs code on your cluster is not the surface a stranger should reach.
- `DEPLOYER_CONSOLE_HOST`, one new required setting validated at startup like every other one. It must be exactly one DNS label followed by `DEPLOYER_APP_DOMAIN` and nothing deeper, so it stays inside the existing wildcard certificate. The console's own base URL is derived from it as `https://` plus the host and is never configured separately, so there is no second place the console's name lives and no way for the two to disagree.
- The public and private split is expressed in the `http.ServeMux` itself, with the host qualified patterns the standard mux has carried since Go 1.22. Every public route is registered a second time under the console host, and one catch all pattern on that host answers `404` for everything else. There is one routing table rather than a table plus a classifier that can drift from it, and a new route nobody remembers to register twice is private rather than public, which is the direction this has to fail in.
- A reserved label set in `internal/domain`, a package constant rather than configuration, holding `admin`, `api`, `app`, `console`, `deployer`, `mcp`, `registry` and `www`. Creating an app whose derived slug lands in that set is refused with the new closed reason code `app_name_reserved`, taking the set from twenty two codes to twenty three. The check runs on the derived slug, so a display name that derives to a reserved label is refused just as a literal one is, and it runs on the create path only: an app that already holds one of those slugs keeps deploying, rolling back and being listed exactly as before, with no migration.
- The tunnel itself, as reviewed manifests under `deploy/`. `cloudflared` runs in its own namespace, `deployer-edge`, with two replicas so a node drain or a rolling update never leaves zero connectors, from a digest pinned image, and its credential exists in the cluster only as a `SealedSecret`. Its routing rules are a `ConfigMap` in this repository rather than a dashboard setting, pinned by a parse test in `internal/config` the same way the static network policies already are, and nothing at run time reads that file.
- The tunnel routes exactly two hostnames and then refuses. The console host goes straight to the `deployer` Service over plain HTTP inside the cluster, skipping `ingress-nginx` entirely, and the app wildcard goes on through `ingress-nginx` over HTTPS with `originServerName` set to the bare app domain and origin verification left on. Anything else meets a catch all that answers `404`, so no other name reaches the cluster through the tunnel.
- Migration `00005_audit_client_address.sql`, one nullable `client_address TEXT` column on `audit_log` and no index, because `audit_log_occurred` already serves every read and an index here would cost a write on every audited action for a query with no caller. The address is carried as a new field on the existing `auth.Audit` value, so every call site kept its shape and sets the address where it builds the struct. A row the platform wrote itself, a suspension sweep, a reconcile drive, a scheduled backup, leaves it null.
- A daily sweep, on the same in process scheduler `internal/backup` already uses, sets `client_address` back to null on every `audit_log` row older than `DEPLOYER_RETENTION_DAYS`, which keeps its existing default of 90. The row itself is never deleted, so the trail survives and the identifier does not. It is one `UPDATE` scanning the table once a day with no supporting index, which is the right cost at this size and is written down rather than discovered.
- `internal/tunnelwatch`, which tells you when the edge has no connectors. It reads `cloudflared`'s own ready endpoint over HTTP through a Service in the tunnel namespace, so it needs no Kubernetes API read and grants the platform no new cluster rights at all. One mail when it breaks and one when it comes back, never one per check, the same discipline the backup alerter holds. With no mailer or no address configured it returns no watcher, the tunnel still works, and the platform simply says nothing about it.

### Changed

- Deployments now walk `queued`, `building`, `pushing`, `deploying`, `healthy`, one recorded transition at a time, with a single reconcile loop as the only writer of state after `queued`. Only one build runs at a time, platform wide.
- Every app workload is composed field by field in Go and referenced by image digest, never by tag. The only caller derived values anywhere in a pod spec are the platform derived slug and the digest of an image the platform itself built.
- The uploaded tarball is deleted once its deployment reaches a terminal state, whichever state that is.
- `deploy_app` returns as soon as the queued deployment is written, carrying `deployment_id`, `name`, `slug`, `url` and `state`. It no longer carries `release_number` or `image_digest`, because neither exists yet; read them from `deployment_status` once the deployment is healthy.
- `DEPLOYER_DEPLOY_TIMEOUT_SECONDS` keeps its name, its default and its startup validation, and now bounds a deployment from creation to a terminal state rather than bounding one MCP call. Queue time counts against it. No new setting was added.
- A deploy waiting its turn now sits in `queued` where a caller can see it. One build at a time, platform wide, was always true; it used to be invisible inside a hung connection.
- Redeploying an app writes `superseded` onto the cancelled deployment's row as well as its event, and the deployment that replaced it is reported as `superseded_by`, derived from the app's next deployment by id rather than by timestamp.
- A drive whose deployment was cancelled underneath it by a redeploy now stops quietly instead of writing over a row something else correctly ended.
- The account row that already owned apps, deployments and uploads became a person, so nothing about ownership changed shape. There is no membership table and no join: a person is exactly one account.
- Network policies are applied on every reconcile, overwriting whatever is there, so a policy someone deleted or weakened by hand comes back on that app's next deploy. This is the one place the platform departs from its create once and never edit rule, and it departs on purpose: the namespace, quota and LimitRange are left alone so the platform cannot move a fence someone tightened, and a policy is rewritten so a fence someone loosened does not stay loose.
- Both policies are written before the Deployment. A policy write that fails ends the deployment with reason `internal` and creates no Deployment, so an app is never running while unpoliced.
- The `build_failed` message no longer names Cloud Native Buildpacks, since either engine can now produce it. It points at `deployment_status`'s `build_path` instead, so a caller knows whether to fix the `Dockerfile` or the project layout.
- `deploy_app`'s tool description states that a root `Dockerfile` is built when present and Buildpacks otherwise. The description is contract, not decoration.
- A configuration change starts no deployment and does not touch the running app. It reaches the container on the next deploy, and every response says so with `applies_on_next_deploy`.
- A release's `config_snapshot` now records what actually ran. The configuration travels from the deploy that composed the Secret and the pod checksum through to the moment the release is cut, rather than being read again at the end, because the readiness wait is long enough for a `set_config` to land in the middle of it.
- `deploy_app`'s tool description carries the `config` argument and the reserved names, and the app contract line about `PORT` now names `PORT` and `APP_URL`. The description is contract, not decoration.
- A rollback supersedes whatever deployment was in flight for that app, cancelling it with reason `superseded` in the same transaction, exactly as a `deploy_app` call does. A later deploy or rollback supersedes a rollback in flight the same way.
- A rollback that fails leaves the deployment failed with its reason, mints no release, and leaves both the app's current release pointer and its configuration unchanged, so one bad recovery attempt cannot poison the history. The platform attempts no undo of the cluster objects it already applied.
- A `set_config` that commits during a rollback's readiness wait is reverted when that rollback succeeds, because marking it healthy replaces the whole configuration set from the snapshot with no version check. This is specified behaviour rather than a race to close, and `rollback_app`'s description says so.
- `deployment_status` called with the id of a deployment whose app has since been deleted now answers `deployment_unknown` rather than an internal error. A deleted app's whole history is unreachable, which is an access decision and reads like any other unknown id. `get_logs`, `get_config`, `list_releases` and `rollback_app` answer `app_unknown` for a deleted app the same way, and the suite pins that rather than assuming it.
- A deleted app's name comes free again for the account, but its slug stays reserved for good, so an app created under the old name gets a new slug and a new hostname. Any link already handed out is dead rather than pointing at someone else's app.
- Every page handler is a thin wrapper over the same `internal/identity` calls and the same `internal/store` methods the JSON and MCP surfaces already use. No page reaches the database or Kubernetes by a path of its own, so a rule, a rate limit or an audit row cannot differ between the browser and the agent. The `/v1` and `/mcp` surfaces are untouched and stay drivable with curl.
- The log bounds gained a browser sized pair beside the existing agent sized ones, in `internal/logs` and still as constants rather than settings, because what fits a page and what fits an agent's context window are two product decisions rather than one knob.
- The apps and releases **Load more** control appends the next page rather than replacing the list, and the token list shows created and expiry rather than leaving both columns blank. Both were found by driving the pages on the real cluster after the feature was otherwise complete.
- A deployment stranded by one of those two faults is ended at the next tick carrying the reason its build Job gave, rather than at the deploy budget carrying `timeout`, so its history says what actually happened and its app stops refusing deletes far sooner. A build that had already succeeded is resumed rather than thrown away. A Job still running, and one whose state cannot be read, are both left exactly as they stand: a row is only ever ended on positive evidence from the cluster, and the absence of an answer is never evidence.
- The loop's claim query falls back to the oldest unclaimed non terminal deployment when no `queued` one is waiting, which is what lets a row handed back be adopted and resumed from whatever state it is in. Queued work still comes first, so a row that keeps stranding cannot get ahead of a fresh deploy, and the deploy budget measured from `created_at` still ends it either way.
- The control plane's `replicas: 1` with `strategy: Recreate` became load bearing rather than incidental. Under two processes a row another process is actively driving looks identical to a stranded one, so the check would end a deployment that was going to succeed. Raising the replica count is now a decision that touches spec 0014, recorded beside the manifest that enforces it.
- Both build namespace policies, the Buildpacks one and the Dockerfile one, are narrowed to TCP 80 and 443. A build fetches dependencies and base images, which is HTTP and HTTPS, so an allow list of two ports is both stronger and simpler there than the ranges an app namespace gets, and it restates no port list, so there is no second copy to drift. A build that wants a dependency over SSH on 22 or a registry on some other port now fails, and it fails loudly at build time rather than quietly at run time.
- The startup policy sweep composes the port bound too, not only the blocked range list, so an app namespace created before this change picks the bound up on a control plane restart with no redeploy. Every bound the allow policy carries has to be passed on both paths, or the sweep walks an existing namespace back to a weaker policy than a deploy would compose.
- `deploy_app`'s tool description names the bound, says that a blocked connection times out rather than failing fast, and points an app that sends mail at a provider's relay on 587. The description is contract, not decoration.
- The control plane's `replicas: 1` with `strategy: Recreate` gains a second thing leaning on it. Spec 0014 already depended on it; the backup startup sweep does too, because one replica is what makes a row still marked running definitionally dead and lets the sweep end it with no sweeper, no grace period and no timer. Raising the replica count now touches both.
- A manual backup fired from the admin page no longer runs on the browser request's context. An admin closing the tab used to cancel the run halfway and then cancel the two things that recover from that, so the row never closed and the alert never sent: the run stayed marked running, the unique index refused every later run, and the schedule skipped every tick, silently, until the pod restarted.
- The session cookie is `__Host-deployer_session`, carrying `Secure` and `Path=/` and no `Domain`, falling back to the unprefixed `deployer_session` without `Secure` on plain HTTP exactly as the CSRF cookie already did. Every session in existence ended when this deployed. That is one sign in for everybody and it is the accepted cost of the rename rather than a bug.
- `DEPLOYER_PUBLIC_URL` narrowed rather than changed. It is still the tailnet address, and it is still what an agent is told to upload to, but the link a person clicks in a verification, reset or invite mail is now derived from `DEPLOYER_CONSOLE_HOST` instead. A build pod resolves names on cluster DNS and cannot see the public hostname, which is why anything inside the cluster still reaches the platform on `DEPLOYER_INTERNAL_URL`.
- The `Origin` and `Sec-Fetch-Site` check accepts two origins rather than one, the console and the tailnet, and refuses a third. The pre sign in CSRF cookie needed no change and got none: it already carries the `__Host-` prefix, so each hostname mints its own nonce and a token minted on one host still cannot satisfy a post to the other.
- The visitor's address is derived in one place, `internal/auth`, and both surfaces that rate limit call it, so the page surface and the JSON surface spend from the same bucket for the same visitor rather than each deriving a key of its own.
- The `deployer-system` network policy gains the tunnel namespace as a peer on container port 8080, keeps the tailscale peer and every other existing one, and stays ingress only. `ingress-nginx` is deliberately not a peer: apps are behind it, the control plane is not, and the console reaches the Service directly. The tunnel namespace carries its own policy in both directions, and the parse test in `internal/config` pins both.
- The control plane's `replicas: 1` with `strategy: Recreate` picks up nothing new here, but the tunnel's `replicas: 2` is now load bearing in the opposite direction and is pinned by a test: one connector means a node drain or a rolling update takes the whole public edge down for the length of it.
- The order of the tunnel's two ingress rules is load bearing and a test pins it. `cloudflared` takes the first rule that matches, and the console host also matches the app wildcard, so a console rule listed second is shadowed and every console request lands on `ingress-nginx` instead. That is what happened on the first flip, and the manifest now carries a comment saying why the order cannot be tidied.

### Security

- Both surfaces, the upload endpoint and MCP, authenticate with the same bearer token, and every `deploy_app` call writes one audit row with the outcome.
- An image whose user is empty or `0` is refused with `image_runs_as_root` before any Kubernetes object for that app is created or updated.
- The build pod runs as the builder image's own non root user with all capabilities dropped, no privilege escalation, `seccompProfile: RuntimeDefault`, `backoffLimit: 0` and a deadline from `DEPLOYER_BUILD_TIMEOUT_SECONDS`.
- The registry credential reaches an app namespace only as an `imagePullSecret` the kubelet consumes; it is never mounted, projected, or exposed as an environment variable in an app pod.
- `deployment_status` is scoped to the caller's account before any field is read, and an id or name that does not exist gets the same answer as one belonging to someone else, so status cannot be used to learn which deployments exist. A refused read writes one audit row; an allowed one writes none.
- A deployment's internal event detail, which can hold a raw cluster message, is dropped at the one projection that builds the status timeline, so no write site can leak it into a response.
- Known limits, stated rather than implied: auth is one seeded token with no revocation path (spec 0004 follow-up, feature 8 owns real minting), and the registry's write credential is mounted into the build container beside code the platform did not author, so a hostile buildpack could push any tag in the registry. Running apps are unaffected because every deploy is by digest.
- The limit above, that auth was one seeded token with no revocation path, is closed. Tokens are minted and revoked per account, a revoked token stops authenticating on the very next request, and the raw value is returned exactly once and never stored.
- Registering with an address that already has an account produces the identical response and body as a fresh registration, and mails that address a sign in prompt rather than a second verification link. No response, timing or status difference lets a caller learn whether an address is registered.
- A wrong password, an unknown address and a disabled account all answer with the single code `credentials_invalid`, and every failure writes an audit row. Signing in to an account with no password hash, which is the bootstrap account, takes the same work as a real password check so the answer is not faster. A registered but unverified account is the one deliberate exception and answers `email_unverified`, so the person is sent to resend rather than to reset. That is a bounded enumeration oracle, accepted knowingly.
- A token held by an account whose email is set but unverified is refused on every surface, MCP and upload alike, with the same answer an invalid token gets. Disabling an account, and changing its password, revoke every live session and every live link it holds in the same transaction as the change.
- Two real registered accounts cannot see each other at all: the second cannot deploy to, read the status of, read logs from, or discover the existence of the first's app, and each refusal is an existing closed reason code recorded in the audit log. The ownership boundary has no admin override: an admin cannot reach another account's app either. Two accounts may each own an app of the same name, because a slug carries a random suffix.
- Sign in failures for one address are refused after five attempts with a backoff that doubles to a ceiling, and registration, sign in, resend and forgot share a token bucket keyed by client address. The client address is the last hop of `X-Forwarded-For` when the request came through the ingress, never the raw connection address, which is the ingress pod for every caller.
- No response body, log line or audit row ever contains a raw token, a raw session id, a raw verification or reset link token, or a password. Every admin action, every token mint and revoke, and every failed sign in writes an audit row naming the acting account and, where there is one, the target.
- A failure to send mail never fails the request that triggered it. The account or the link is still created and the failure is logged at error level, so a mail outage cannot become an account that half exists.
- An app can no longer reach another app's pod IP or Service IP, the Kubernetes API server, the in cluster registry, the control plane's internal URL, a node IP, or any other address on the home LAN including the ingress load balancer, so an app cannot call its own or a sibling's public hostname. It can still resolve public names and reach public hosts. Proved live with a probe app deployed twice, not only in unit tests.
- App to app isolation rides on the blocked range list rather than on a rule of its own, because another app's pod IP and Service IP sit inside those ranges. Narrowing that list for an unrelated reason therefore weakens app to app isolation as a side effect, which is why it is validated as a whole rather than treated as a tuning knob.
- Egress is allow by exception. A new destination becomes reachable only by removing a range from the blocked list, never by an app asking for it.
- A unit test pins that the composed pod specs carry no `hostNetwork`, `hostPID`, `hostIPC`, `privileged`, `hostPath` volume or added capability, and that `deploy.Input` has no free form passthrough at all: no map, no annotations, no environment passthrough, no override of any kind. That absence is what makes a privileged request unexpressible rather than merely rejected.
- The looser pod security the Dockerfile path needs is a short list of named deviations on one pod in one namespace rather than a general relaxation. BuildKit's deviations from `baseline` are exactly four and all four are named, its capability bounding set is exactly `SETUID` and `SETGID`, and a test fails if a fifth field appears. The Buildpacks pod still satisfies every `restricted` field. A BuildKit Job that lands in the wrong namespace by mistake is refused by admission rather than run, so a routing bug is a create failure the platform reports rather than a build that quietly runs in the wrong place.
- A Dockerfile can finally produce an image that runs as root, so the `image_runs_as_root` refusal spec 0004 wrote and could never reach became live here. It is decided before a single app object is composed. Neither build path receives build arguments or build secrets, and the BuildKit pod automounts no service account token and holds the same single use registry credential, collected with its Job.
- `list_releases` reads through its own query projecting five named columns and never the release's configuration snapshot, so no configuration value enters the process at all. Both release tools resolve the app within the calling account and answer `app_unknown` for a name that does not exist and for one belonging to someone else alike, and a release number is only looked at after ownership is settled.
- A value marked secret comes back as its key plus the flag, with no value, in every MCP response without exception, including the response to the call that just set it. The value is nulled in SQL rather than in Go, so no code path can forget.
- `get_logs` now blanks exact secret values as well as the shapes it already matched: the app's current secret values and the values the running release was given for keys that are secret today, so a rotated secret the running pod already printed is still blanked. A value under eight characters is not literal matched, because blanking a short string destroys the log without protecting anything worth protecting.
- All three configuration tools resolve the app within the calling account and answer `app_unknown` for a name that does not exist and for one belonging to someone else alike, so no tool tells a caller whether another account's app exists.
- Every configuration change writes an audit row with `target_type` of `app_config` and `target_id` of the app id and the key joined by a slash. No row ever holds a value, and a refusal is recorded with its reason code.
- No build receives configuration. Neither the Buildpacks path nor the Dockerfile path is given build arguments or build secrets, and a test holds that absence in place.
- An app's outbound path to the internet is bounded by port as well as by address. Spam straight to a mail exchanger and the common mining pool ports are the two abuses that cost you a relationship with your internet provider rather than just some CPU, and both are closed by default for every app on the platform. Proved on the real cluster rather than only against the fake clientset: all four probe targets read reached before the change, then 25 and 3333 read timeout while 443 and 587 still read reached, with the app still serving.
- The public egress rule stays exactly one peer, pinned by a test. A `ports` list applies to every peer under the same `to`, so a second peer added beside it would silently inherit the bound and quietly widen what the rule permits.
- Every composed port entry states its protocol explicitly. `NetworkPolicyPort.Protocol` defaults to TCP when it is nil, so a UDP entry composed without it would mean all TCP on any port and reopen the whole bound in a single missing field. UDP is left unbounded on purpose: the bound is about TCP services, and narrowing UDP would break HTTP/3 and time synchronisation for no matching benefit.
- The `config` Secret lives in the app's own namespace, which the app cannot read: it has no Kubernetes token at all, only the environment it was started with.
- `list_apps` is scoped to the calling account before any row is read, and the admin flag widens nothing, the same as every other MCP tool. A successful listing writes no audit row because a read is not an access decision; a refused one writes a `denied` row with action `app_list`.
- A `delete_app` writes an audit row on both outcomes, allowed and refused alike, because a delete removes an app and everything it was serving. A refusal for an app that does not exist, for another account's app, and for one already deleted are all `app_unknown` word for word the same, so the tool cannot be used to learn which app names exist.
- No configuration key and no value appears anywhere in the app listing. The query projects only the columns the listing reports and never reads `app_config` or a release's `config_snapshot`, so no value enters the process at all rather than being withheld by a handler that remembered to.
- A delete retires the app's row before it calls the cluster, so there is no path that tears a namespace down for an app whose row is still live. The database rows the delete deliberately keeps, the deployments, their events, the releases and the configuration, stay readable to nothing: every tool answers `app_unknown` for a deleted app.
- More known limits, stated rather than implied: the reaper deletes namespaces on a timer with no human in the loop, so a bug in its guards is destructive rather than merely wrong, which is why each guard is pinned by its own test. A namespace delete that fails after the row is already retired leaves the caller told `internal` and the namespace standing until a later reaper pass finishes the job, so the two halves of a delete are not atomic and never can be. A local run with no cluster credential reads the same way, deliberately.
- More known limits, stated rather than implied: the platform is now unambiguously a secret store, and values sit in clear in the SQLite file, in every release snapshot, and by k3s default in etcd, which the deferred backup and restore item now has to guard. Marking a value secret is the caller's job, so an agent that forgets the flag puts a credential in a response and in the logs. A key flipped from secret back to plain stops protecting what the running pod already printed under it.
- Pages authenticate with the session cookie alone. A request carrying a bearer API token instead of a session is treated as signed out on every page, so a leaked agent token cannot open the browser surface. A signed out visitor to a gated page is redirected to `/login?next=<path>`, and a sign in follows `next` only when it is a local path beginning with exactly one `/`.
- Every state changing POST by a signed in person carries a hidden `csrf` field, the hex HMAC SHA256 of the session id under `DEPLOYER_CSRF_KEY`, recomputed and compared in constant time. It is derived at render and never stored, so it is valid exactly as long as its session and is revoked by the same act. A missing or wrong value answers `403`, changes nothing, and writes an audit row.
- Every POST to a page path is refused `403` when `Origin` is present and is not the platform's own, and when `Sec-Fetch-Site` is present and is neither `same-origin` nor `none`. A request carrying neither header passes, which is stated knowingly rather than overlooked: every browser able to perform a cross site form post sends `Sec-Fetch-Site: cross-site`, and a scripted client omitting both carries no session cookie either. The pre authentication posts, which have no session to bind a token to, are guarded by this check alone.
- The browser is never a weaker door than the agent surface. Anything MCP refuses to return, a page refuses to render, and a control merely absent from a template is not a guard: the route refuses it too. A secret flagged configuration value has no reveal control and no route that returns it, so `store.ListConfigForDeploy` gains no third caller, and revealing a value that is not flagged writes an audit row naming the account, the app and the key.
- Ownership on the pages is the same account scoped store methods the MCP tools use rather than a check of its own. Another account's app slug renders the identical not found page an unknown slug renders, with an audit row, on all four app pages. Admin widens nothing: an admin gets the accounts list and the three admin actions and no override on app ownership.
- No rendered page, no template, no redirect URL and no log line at info level carries a raw API token, a raw session id, a raw verification or reset link token, a password, or a secret configuration value. A crawl of every page as a signed in account asserts it rather than the rule being trusted.
- One more known limit, stated rather than implied: the status fragment's fifteen minute polling ceiling is a client behaviour only. A client ignoring it costs one indexed session gated query per poll and nothing else.
- Nothing in the cluster can read a backup. The platform holds the public age recipient and nothing else: there is no configuration value, no Secret and no code path that gives it a private identity, so a bucket credential leaking hands nobody a password hash, a token or an app secret, and neither does anything that compromises the platform itself. age is the Go library linked into the binary rather than a command line tool run as a subprocess, because the image has no shell and a subprocess would be a second thing to pin.
- The plaintext never leaves the volume. The snapshot is checked and encrypted on disk and only the encrypted file is uploaded. Both temporary files live under one fixed directory at mode 0700 and are removed on every exit path, success and failure alike, and the directory is emptied again at startup, because a hard kill runs no exit path and what it leaves behind is a full unencrypted copy of every password hash, session, token and app secret sitting there indefinitely, visible to no surface this feature builds.
- The snapshot's own mode is set rather than assumed. SQLite creates that file, not the platform, so it lands world readable under the usual umask; it is tightened to 0600 as soon as it exists. Found by driving the real cluster, not by the test suite, and pinned by a test afterwards.
- A backup alert carries the closed reason code and nothing else: no object key, no bucket name, no configuration value. A failure notification is not a place to leak where the backups are, and the errors that can reach one are written without those details rather than filtered on the way out.
- The bucket carries an object retention rule of seven days, so no caller can delete a backup in its first week whatever its credential permits. That is stronger than a credential scoped to write but not delete, which R2 cannot express in any case, because it holds against a token somebody re issues later rather than depending on nobody doing so.
- `deployer restore` reads the age identity from a file named by a flag, never from an environment variable and never from an argument, so the one private key in the whole design does not land in a process listing. A parse failure says the file does not hold an identity and quotes none of it.
- A refusal from the backup path is a real access decision or a real reason code, never a masked internal error. The one run at a time refusal is recognised by matching the unique constraint violation specifically: a full volume, a locked database or any other write fault is `internal` and is alerted as such, because reporting a real fault to an admin as a benign concurrency refusal is how this feature would lie about its own health.
- More known limits, stated rather than implied: a release's `config_snapshot` still holds live third party credentials in clear text inside the database, so shipping backups multiplies that rather than reducing it. There are now up to thirty encrypted copies of every secret anyone ever set, and the plaintext is still plaintext inside each one. Encrypting configuration values at rest is a change to the deploy path, the rollback path and `MarkHealthy` at once and needs its own key custody decision, so it is recorded as owed rather than done.
- One more, on the other half: the registry volume goes to the same bucket through Longhorn, which encrypts at the volume level rather than at the backup, so those blobs land off site in plaintext. They are user application images rather than platform secrets, which is why it is accepted here, and fixing it means migrating the volume to an encrypted StorageClass rather than setting a flag.
- And one on what the platform cannot see: the registry backup lives in `k3sprox-gitops` and the sealed secrets key export lives in your hands, so nothing here can tell whether either actually happened. Whether the platform should check that a registry backup exists, or whether that stays a habit, is recorded as a decision rather than assumed either way.
- Everything the open internet can reach is the page surface. Every admin page, `/mcp` and every `/v1` path answers `404` on the console hostname, changes nothing, and writes no audit row, because no caller has been identified at that point. They are absent from the mux on that host rather than refused by a check inside a handler, so the refusal cannot be forgotten in one route. Administering the platform means signing in on the tailnet name, and the console renders no link, no navigation entry and no button to any page it would answer `404` for.
- `CF-Connecting-IP` is read on exactly one hostname and nowhere else, and what makes that safe is the path rather than the header. The console origin is the `deployer` Service directly rather than the shared ingress controller, so network policy can name the tunnel namespace, the tailscale proxy and the two build namespaces as the only pods that may open a connection to it. Forging the header needs a pod in one of those, and the only one a user influences is a build pod, which is short lived and holds no session, so the most it could buy is a wrong address on an audit row for an action it cannot take. Moving the console behind `ingress-nginx` would make the header writable from most of the cluster and nothing in the suite would notice.
- More than one `CF-Connecting-IP` value is treated as the header being absent, and the ordinary derivation is used. Cloudflare sends exactly one, so more than one means something else wrote it.
- The session cookie carries the `__Host-` prefix because the console is now a sibling of subdomains running code the platform did not write. Without it an app deployed by a stranger can set a parent scoped cookie of the same name and the console reads it, which is session fixation with a deploy as the delivery mechanism.
- That protection was defeated for a day by the reader rather than the writer. `auth.SessionID` tried both cookie names, secure first, so the unprefixed `deployer_session` still authenticated: the rename ended nobody's session, and a cookie scoped to the parent domain by an app was accepted by the console. Driven in a clean browser holding only that cookie at the parent domain, the console answered 200 with the signed in page. It now reads the one name the platform's own scheme selects, the same way the write already picked it, and the test that had required both names to resolve was the bug written down as an assertion.
- The account lockout on sign in was in the JSON handler alone. `Service.Login` touched the limiter nowhere, so the browser counted no failures and honoured no penalty while a comment claimed it inherited both, and each surface's tests only ever asserted its own behaviour. This feature is what made it bite, because the JSON surface answers `404` on the console hostname, so the surface with no lockout became the only one on the open internet, bounded only by a per address bucket refilling one token every six seconds. Measured live: the JSON surface answered 401 five times then 429, and the browser answered 401 eight times for the same address while that address was already locked out. Every rule a sign in is refused by now lives in `Service.Login`, removed from the handler rather than left in both, so one wrong password is not counted twice.
- The address in `audit_log` is personal data and is treated as such. It exists for the retention window and is then nulled in place, which does mean that after the window a nulled row and a row the platform wrote itself are indistinguishable. That is accepted and written into the spec, so a person reading an old denial knows why the address is missing.
- Cluster administration is published by nothing here. The Kubernetes API, ArgoCD, Longhorn and the registry stay on the tailnet, and the tunnel's two routes plus a catch all that refuses are the proof rather than the intention.
- A deployed app receives the forwarded chain unchanged, so it reads `X-Forwarded-For` and, when it cares, `CF-Connecting-IP`. No app manifest, no controller wide setting and no Go code changes for this, and the header is documented rather than rewritten: an app has no reason to trust it, and the documentation says so.
- More known limits, stated rather than implied: `ingress-nginx` remains a shared controller serving your other cluster apps, and an `Ingress` object applied anywhere could still name the `deployer` Service as its backend. That was already true of the tailnet path, it is now stated rather than assumed, and it is one more reason the console does not go through that controller. Two hostnames also means two host scoped sessions, so a person who administers the platform signs in twice, which is the intended consequence rather than an oversight.
