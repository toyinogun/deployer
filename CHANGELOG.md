# Changelog

All notable changes to this project are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- First deploy end to end: an agent can upload a source tarball, call one MCP tool, and get back a working HTTPS hostname for the running app (see spec 0004).
- `deploy_app` MCP tool, taking `name` and `upload_id`. It builds the source with Cloud Native Buildpacks in a Kubernetes Job, pushes the image to the in cluster registry, composes the app's Deployment, Service and Ingress, waits for the app to answer, and returns the name, slug, URL and deployment id. The call does not wait for the build; `deployment_status` reports the outcome (see spec 0005 below).
- `POST /v1/uploads`, which accepts a gzipped tar body against a bearer token, rejects a body over `DEPLOYER_MAX_UPLOAD_BYTES` with 413 before writing it all to disk, records the size and SHA-256, and returns the upload id and its expiry.
- `GET /v1/uploads/{id}`, a single use redeem path used only by the build Job's init container to fetch the tarball.
- `fetch-source` subcommand, run as the build Job's init container. It verifies the recorded SHA-256 before unpacking and refuses any archive entry with an absolute path, a `..` component, a symlink, a hardlink or a device node, along with any archive over the file count or uncompressed size caps.
- Redeploying an app under the same name keeps the same hostname and increments the release number, so a link already handed to someone keeps working.
- A closed set of failure reason codes on every failed deploy (`upload_invalid`, `upload_expired`, `source_rejected`, `build_failed`, `build_no_digest`, `image_runs_as_root`, `app_never_ready`, `timeout`, `internal`), returned to the caller and stored on the deployment. Raw build output never reaches the response, the database, or the platform log at info level.
- A startup sweep that reconciles every non terminal deployment against the cluster, so a control plane restart during a build resumes a live Job and fails one that has vanished, rather than leaving a deployment stuck.
- An in cluster container registry (`distribution` v3) in `deployer-system`, backed by a Longhorn volume, with htpasswd auth held only as a `SealedSecret`, and no Ingress. Plus the `deployer-builds` namespace with `enforce: restricted` pod security.
- Bootstrap seeding at startup: when `DEPLOYER_BOOTSTRAP_TOKEN` is set, the platform ensures one `bootstrap` account and one token row holding that token's SHA-256 hash. Running it again changes nothing, and the raw token is never logged.
- New settings, all validated at startup so a missing or malformed one fails the boot naming the variable: `DEPLOYER_BOOTSTRAP_TOKEN`, `DEPLOYER_PUBLIC_URL`, `DEPLOYER_INTERNAL_URL`, `DEPLOYER_BUILDER_IMAGE`, `DEPLOYER_SELF_IMAGE`, `DEPLOYER_BUILD_UID`, `DEPLOYER_BUILD_GID`, `DEPLOYER_DEPLOY_TIMEOUT_SECONDS`, `DEPLOYER_BUILD_TIMEOUT_SECONDS`, `DEPLOYER_READY_TIMEOUT_SECONDS`, `DEPLOYER_RECONCILE_INTERVAL_SECONDS`, `DEPLOYER_APP_DEFAULT_CPU`, `DEPLOYER_APP_DEFAULT_MEMORY`, `DEPLOYER_APP_LIMIT_CPU`, `DEPLOYER_APP_LIMIT_MEMORY`, `DEPLOYER_MAX_UPLOAD_FILES`, `DEPLOYER_MAX_EXTRACTED_BYTES`.
- A CI step that reads the pinned builder image's own `CNB_USER_ID` and `CNB_GROUP_ID` and fails on drift from `DEPLOYER_BUILD_UID` and `DEPLOYER_BUILD_GID`.
- `testdata/sample-go`, a minimal sample app used to prove the whole path against the real cluster.
- Async deployment jobs and status: the deploy call stops waiting, so a client's request timeout has nothing to do with how long a build takes (see spec 0005).
- `deployment_status` MCP tool, taking exactly one of `deployment_id` or `name`. It reports the deployment's state and a timeline of every recorded transition, plus the release number and image digest once healthy, the reason code and its one line when failed, and `superseded` with the id that replaced it when cancelled. Polling it every few seconds is the intended shape, and its description says so.
- A watchdog inside the reconcile loop, which fails any deployment that runs past `DEPLOYER_DEPLOY_TIMEOUT_SECONDS` with reason `timeout` and deletes its build Job. Every deployment now ends by itself, which the blocking call used to cover by giving up.
- Two more failure reason codes, `deployment_unknown` and `superseded`, taking the closed set from nine to eleven. `superseded` describes a cancellation rather than a failure.
- A fetch of an upload whose tarball has already been deleted answers `410 Gone` in the same words as an expired upload, rather than an internal error. That path became reachable once the watchdog could delete a tarball while a build was still fetching it.
- Application logs: an agent can read back the output of an app it deployed, so a misbehaving app can be debugged without anyone opening a terminal (see spec 0006).
- `get_logs` MCP tool, taking an app `name` and an optional `tail_lines`. It returns the newest lines still on the node, oldest first, each with the timestamp the kubelet recorded. It is a snapshot, not a stream: no follow, no search, no time window. `tail_lines` defaults to 200 and is capped at 1000, and a larger ask is clamped rather than refused, with the response echoing the value applied. The answer is capped by size as well as by line count; when the size cap is hit the oldest lines go, never the newest, and `truncated` and `dropped` say so.
- An app that crashed and restarted gets a second, smaller block of the dead container's output in `previous`, capped independently of the current block so restart noise can never squeeze the crash out of the answer. It is absent when there has been no restart.
- Secrets are blanked before the lines are returned, on a best effort basis the tool description states plainly: bearer and basic credentials, JWTs, passwords inside URLs, AWS style access key ids, and assignments named like a key, token, secret, or password. The registry credential the platform placed in the app's namespace is matched exactly, because that is the one value the platform knows for certain is secret. High entropy alone is deliberately not a trigger, because blanking on it destroys ordinary output.
- An app with no container started yet is a success with no entries, carrying the deployment's current state and one sentence saying why there is nothing to show. That is what every read during a build sees, and it now reads the same way whether the app's namespace is missing or merely not readable by the platform yet.
- One more reason code, `app_unknown`, taking the closed set from eleven to twelve. A log read for a name that does not exist and one for an app belonging to another account get the same answer, so the tool cannot be used to learn which app names exist. Only a refusal is audited; a successful read is not an access decision.
- No new settings. The log bounds are constants, because they are decisions about what fits an agent's context window rather than per deployment tuning, and nothing about a log read is stored: the platform reads from Kubernetes at the moment of the call and hands the lines back.
- App environment configuration: an app can be given the values it was written against, so anything needing an API key or a database address is deployable here at all (see spec 0010).
- `set_config` MCP tool, taking an app `name` and a `config` map of key to `{value, secret}`. It merges the keys into whatever is already set, in one transaction, and returns the resulting configuration. Every key needs its `secret` flag; a key sent without one is refused with `config_flag_missing`, so re setting an existing key can never quietly turn a secret into a plain value.
- `unset_config` MCP tool, taking an app `name` and a list of `keys`. It removes them in one transaction. If any key in the call is not set, the whole call is refused with `config_key_unknown` and nothing is removed.
- `get_config` MCP tool, listing every key with its secret flag, and its value only when the key is not secret.
- `deploy_app` gains an optional `config` map of the same shape, validated by exactly the same rules and written before the deployment row is created, so a brand new app's first run is not a guaranteed crash on a missing variable. A call carrying no map leaves the configuration untouched.
- A deploy composes one Kubernetes Secret named `config` in the app's namespace holding every configured key and value, and the container receives them with `envFrom`. The values are read once, when the workload is composed, so a change landing mid build reaches that same deploy and nothing later moves under it.
- `APP_URL` is injected beside `PORT`, built from the same host the Ingress rule takes, so an app can build a link to itself on its first run. Both are composed by the platform and neither can be stored: `PORT` and `APP_URL` are refused with `config_key_reserved`.
- The pod template carries an annotation holding a checksum of the configuration it was composed with, so a deploy whose image digest is unchanged still rolls the pods and the new values actually reach the container.
- Configuration is bounded: 64 keys for one app, 4 KB for one value, 32 KB for the whole set, refused with `config_too_many_keys` and `config_too_large`. A key must match `[A-Z_][A-Z0-9_]*` or it is refused with `config_key_invalid` before any write, so the database constraint is a backstop rather than the error reporter. An empty string is a valid value and is not the same thing as the key being unset.
- Six more reason codes, `config_key_invalid`, `config_key_reserved`, `config_key_unknown`, `config_flag_missing`, `config_too_many_keys` and `config_too_large`, taking the closed set from twelve to eighteen. Every one of them is decided before any write, so a refused call changes nothing.
- No new settings and no migration. The bounds are Go constants, because they are decisions about what an app should carry rather than knobs for whoever runs the platform, and the `app_config` table and the release's `config_snapshot` column were designed for this back in spec 0002.
- `testdata/envprint`, a sample app that prints its own environment, used to prove the values reach a real container.
- App lifecycle, list and decommission: an agent can see what it has deployed and tear an app down cleanly, which matters most when it is generating throwaway apps (see spec 0012).
- `list_apps` MCP tool, taking no arguments at all: the account comes from the token and the bound is the platform's. Each app reports its name, slug, url and creation time, plus two separate facts that reading as one is the mistake the listing exists to prevent. `serving` is the release the app is running right now, and `last_deployment` is how the most recent deploy ended. An app whose last deploy failed is usually still serving its previous release, so a row carrying both a serving release and a failed last deployment means the app is up and the new version is not. An app never healthy has no `serving` object, one never deployed has no `last_deployment` object, and a deploy still running appears with its live state. It returns at most the newest 50 apps and there is no way to page past them, which its description says plainly.
- `delete_app` MCP tool, taking an app `name`. One Kubernetes call deletes the app's whole namespace, which cascades the Deployment, Service, Ingress, Secret, both NetworkPolicies, the ResourceQuota, the LimitRange and the RoleBinding together. Nothing is deleted object by object. The call does not wait for the cluster to finish terminating, and returns once the delete is recorded and issued.
- An orphan namespace reaper, the platform's first unattended destructive loop. It runs on its own ticker and once at startup, and deletes every app namespace the platform owns whose slug matches no live app row. Every guard on it is load bearing: only namespaces carrying both of the platform's labels are considered at all, a namespace younger than the grace is out of reach, and a live slug read that fails aborts the whole pass rather than reading as nothing owning anything. One namespace that will not delete is logged and stepped over so the rest of the pass still runs.
- One more reason code, `deployment_in_flight`, taking the closed set from nineteen to twenty. A delete of an app with a deploy or rollback still running is refused whole: nothing is written and nothing is torn down, because tearing the namespace down now would pull it out from under a build writing into it.
- Two new settings, both validated at startup like every other one: `DEPLOYER_REAP_INTERVAL_SECONDS`, how often the reaper runs, ten minutes by default, and `DEPLOYER_ORPHAN_GRACE_SECONDS`, how old a namespace must be before a pass may consider it, fifteen minutes by default. Neither has any required relationship to the deploy timeout, because an app's row is live for the whole of every build and so an app mid deploy is never a candidate whatever these are set to.

### Changed

- Deployments now walk `queued`, `building`, `pushing`, `deploying`, `healthy`, one recorded transition at a time, with a single reconcile loop as the only writer of state after `queued`. Only one build runs at a time, platform wide.
- Every app workload is composed field by field in Go and referenced by image digest, never by tag. The only caller derived values anywhere in a pod spec are the platform derived slug and the digest of an image the platform itself built.
- The uploaded tarball is deleted once its deployment reaches a terminal state, whichever state that is.
- `deploy_app` returns as soon as the queued deployment is written, carrying `deployment_id`, `name`, `slug`, `url` and `state`. It no longer carries `release_number` or `image_digest`, because neither exists yet; read them from `deployment_status` once the deployment is healthy.
- `DEPLOYER_DEPLOY_TIMEOUT_SECONDS` keeps its name, its default and its startup validation, and now bounds a deployment from creation to a terminal state rather than bounding one MCP call. Queue time counts against it. No new setting was added.
- A deploy waiting its turn now sits in `queued` where a caller can see it. One build at a time, platform wide, was always true; it used to be invisible inside a hung connection.
- Redeploying an app writes `superseded` onto the cancelled deployment's row as well as its event, and the deployment that replaced it is reported as `superseded_by`, derived from the app's next deployment by id rather than by timestamp.
- A drive whose deployment was cancelled underneath it by a redeploy now stops quietly instead of writing over a row something else correctly ended.
- A configuration change starts no deployment and does not touch the running app. It reaches the container on the next deploy, and every response says so with `applies_on_next_deploy`.
- A release's `config_snapshot` now records what actually ran. The configuration travels from the deploy that composed the Secret and the pod checksum through to the moment the release is cut, rather than being read again at the end, because the readiness wait is long enough for a `set_config` to land in the middle of it.
- `deploy_app`'s tool description carries the `config` argument and the reserved names, and the app contract line about `PORT` now names `PORT` and `APP_URL`. The description is contract, not decoration.
- `deployment_status` called with the id of a deployment whose app has since been deleted now answers `deployment_unknown` rather than an internal error. A deleted app's whole history is unreachable, which is an access decision and reads like any other unknown id. `get_logs`, `get_config`, `list_releases` and `rollback_app` answer `app_unknown` for a deleted app the same way, and the suite pins that rather than assuming it.
- A deleted app's name comes free again for the account, but its slug stays reserved for good, so an app created under the old name gets a new slug and a new hostname. Any link already handed out is dead rather than pointing at someone else's app.

### Security

- Both surfaces, the upload endpoint and MCP, authenticate with the same bearer token, and every `deploy_app` call writes one audit row with the outcome.
- An image whose user is empty or `0` is refused with `image_runs_as_root` before any Kubernetes object for that app is created or updated.
- The build pod runs as the builder image's own non root user with all capabilities dropped, no privilege escalation, `seccompProfile: RuntimeDefault`, `backoffLimit: 0` and a deadline from `DEPLOYER_BUILD_TIMEOUT_SECONDS`.
- The registry credential reaches an app namespace only as an `imagePullSecret` the kubelet consumes; it is never mounted, projected, or exposed as an environment variable in an app pod.
- `deployment_status` is scoped to the caller's account before any field is read, and an id or name that does not exist gets the same answer as one belonging to someone else, so status cannot be used to learn which deployments exist. A refused read writes one audit row; an allowed one writes none.
- A deployment's internal event detail, which can hold a raw cluster message, is dropped at the one projection that builds the status timeline, so no write site can leak it into a response.
- Known limits, stated rather than implied: auth is one seeded token with no revocation path (spec 0004 follow-up, feature 8 owns real minting), and the registry's write credential is mounted into the build container beside code the platform did not author, so a hostile buildpack could push any tag in the registry. Running apps are unaffected because every deploy is by digest.
- A value marked secret comes back as its key plus the flag, with no value, in every MCP response without exception, including the response to the call that just set it. The value is nulled in SQL rather than in Go, so no code path can forget.
- `get_logs` now blanks exact secret values as well as the shapes it already matched: the app's current secret values and the values the running release was given for keys that are secret today, so a rotated secret the running pod already printed is still blanked. A value under eight characters is not literal matched, because blanking a short string destroys the log without protecting anything worth protecting.
- All three configuration tools resolve the app within the calling account and answer `app_unknown` for a name that does not exist and for one belonging to someone else alike, so no tool tells a caller whether another account's app exists.
- Every configuration change writes an audit row with `target_type` of `app_config` and `target_id` of the app id and the key joined by a slash. No row ever holds a value, and a refusal is recorded with its reason code.
- No build receives configuration. Neither the Buildpacks path nor the Dockerfile path is given build arguments or build secrets, and a test holds that absence in place.
- The `config` Secret lives in the app's own namespace, which the app cannot read: it has no Kubernetes token at all, only the environment it was started with.
- `list_apps` is scoped to the calling account before any row is read, and the admin flag widens nothing, the same as every other MCP tool. A successful listing writes no audit row because a read is not an access decision; a refused one writes a `denied` row with action `app_list`.
- A `delete_app` writes an audit row on both outcomes, allowed and refused alike, because a delete removes an app and everything it was serving. A refusal for an app that does not exist, for another account's app, and for one already deleted are all `app_unknown` word for word the same, so the tool cannot be used to learn which app names exist.
- No configuration key and no value appears anywhere in the app listing. The query projects only the columns the listing reports and never reads `app_config` or a release's `config_snapshot`, so no value enters the process at all rather than being withheld by a handler that remembered to.
- A delete retires the app's row before it calls the cluster, so there is no path that tears a namespace down for an app whose row is still live. The database rows the delete deliberately keeps, the deployments, their events, the releases and the configuration, stay readable to nothing: every tool answers `app_unknown` for a deleted app.
- More known limits, stated rather than implied: the reaper deletes namespaces on a timer with no human in the loop, so a bug in its guards is destructive rather than merely wrong, which is why each guard is pinned by its own test. A namespace delete that fails after the row is already retired leaves the caller told `internal` and the namespace standing until a later reaper pass finishes the job, so the two halves of a delete are not atomic and never can be. A local run with no cluster credential reads the same way, deliberately.
- More known limits, stated rather than implied: the platform is now unambiguously a secret store, and values sit in clear in the SQLite file, in every release snapshot, and by k3s default in etcd, which the deferred backup and restore item now has to guard. Marking a value secret is the caller's job, so an agent that forgets the flag puts a credential in a response and in the logs. A key flipped from secret back to plain stops protecting what the running pod already printed under it.
