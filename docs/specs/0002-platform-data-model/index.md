# 0002. Platform data model for accounts, apps, deployments, and releases

**Date**: 2026-08-11
**Status**: Accepted

## Summary

This decides the shape of Deployer's own database: nine tables in one SQLite file that record who is calling, what apps exist, every deployment and the states it moved through, and which image plus configuration was last known good. Everything is designed now, in a single migration, because later slices need to add behaviour rather than reopen the schema, and because the database has no backup yet, so a migration against live data is the thing to avoid. A deployment walks a fixed set of states, every move is written as a row before it becomes an action, and a release is only created when a deployment actually becomes healthy, which is what makes a rollback able to re promote an exact image and its exact environment. Apps are never truly deleted, so their hostname is never handed to somebody else's app.

Reasoning, the options weighed, and the tradeoffs consciously accepted: see [rationale.md](rationale.md).

## Requirements

**User stories**:

- As an AI coding agent, I want each deployment to have a stable id and a precise current state so that I can ask how my deploy is going and get an answer I can act on.
- As an AI coding agent, I want the platform to remember which release was healthy so that I can roll back to the exact app that worked, not just an old image.
- As the platform operator, I want ownership, denials, and lifecycle changes recorded so that I can answer who deployed what, and who was refused, after the fact.
- As the engineer building later slices, I want the schema already correct so that adding tokens, configuration, or rollback is new code rather than a migration against live data.

**Acceptance criteria**:

- **AC-1**: One `goose` migration creates all nine tables on an empty database file. `goose up` followed by `goose down` returns the file to empty, both without error.
- **AC-2**: The database is opened with WAL journaling, `foreign_keys=ON`, and a busy timeout of `DEPLOYER_DB_BUSY_TIMEOUT_MS` (default 5000), set once at open, on every connection the pool hands out.
- **AC-3**: Every primary key is a prefixed, time sortable text id generated by one `internal/ids` package. Ids generated in the same millisecond are distinct, and sorting ids as text sorts them by creation time.
- **AC-4**: `deployments.state` accepts only `queued`, `building`, `pushing`, `deploying`, `healthy`, `failed`, `cancelled`. A write of any other value is rejected by the database, not only by Go.
- **AC-5**: Every state change writes the updated `deployments` row and exactly one `deployment_events` row inside a single transaction. If either write fails, neither is applied. This includes the first event, written by `Create` with `from_state` null and `to_state` `queued`, and the event written on a superseded deployment when it is cancelled.
- **AC-6**: An illegal transition (for example `healthy` back to `building`, or any move out of a terminal state) is refused by the transition function and writes nothing.
- **AC-7**: At most one non terminal deployment exists per app at any time. Creating a deployment while one is in flight moves the in flight one to `cancelled` with reason `superseded`, writing its event row, and creates the new one, all in one transaction.
- **AC-8**: The reconcile claim (`UPDATE ... WHERE state = 'queued' AND claimed_at IS NULL`) claims a given row at most once when two callers race, and the loser sees zero rows affected. `claimed_by` records the claiming pod.
- **AC-9**: Marking a deployment `healthy` writes the row update, its event row, exactly one `releases` row carrying the image digest read from the deployment row and a JSON snapshot of that app's configuration, with `release_number` one greater than that app's previous highest, and the update to `apps.current_release_id`, all in one transaction and one store call. There is no window in which a `healthy` deployment has no release.
- **AC-10**: A rollback deployment carries `source_release_id` set and `upload_id` null, receives its `image_digest` from that release at creation rather than from a push, and walks `queued` to `deploying` to `healthy`, skipping `building` and `pushing`. Its release records the same digest as the release it re promotes.
- **AC-11**: An app slug is unique across every app row that has ever existed, including soft deleted ones. Two apps created under the same account with the same name receive different slugs. A suffix collision is retried with a fresh suffix up to five times before the create fails.
- **AC-12**: Soft deleting an app sets `deleted_at` and leaves its deployments, events, and releases in place. The app listing and lookup queries exclude soft deleted apps by default.
- **AC-13**: An API token is stored only as a hash plus a short non secret prefix. Lookup by hash resolves the owning account. A revoked, expired, or unknown token resolves to no account.
- **AC-14**: Every authorization outcome writes one `audit_log` row, including a denial where no account resolved, in which case `account_id` is null.
- **AC-15**: The store's configuration read path used for tool responses returns every key with its `is_secret` flag, the value for non secret keys, and no value at all for secret keys. Only the deploy path reads secret values.
- **AC-16**: A delete that would orphan a child row fails with a foreign key error. Nothing cascades. A deployment carrying exactly one of `upload_id` or `source_release_id` is accepted; one carrying both or neither is rejected by a CHECK constraint.
- **AC-17**: The retention sweep, driven by `DEPLOYER_RETENTION_DAYS`, deletes failed and cancelled deployments whose `finished_at` is past the cutoff together with all their events regardless of those events' own age, then deletes remaining `deployment_events` whose `occurred_at` is past the cutoff, then deletes `uploads` that are redeemed or expired and older than 24 hours. Children are always deleted before parents. `releases` and `audit_log` are never touched.
- **AC-18**: The store package is exercised against a real SQLite file in a temporary directory. No part of the store is mocked.

## Decision

**Chosen option**: Option 1: Full normalised model, nine tables, transitions as an event log.

Nine tables land in one `goose` migration on an empty database: `accounts`, `api_tokens`, `apps`, `app_config`, `uploads`, `deployments`, `deployment_events`, `releases`, `audit_log`. Current state lives on the row, history lives in append only event and audit tables, enumerated values are policed by CHECK constraints, and which transitions are legal lives in one Go function that writes the row and its event in the same transaction.

**Implementation skills**: `database-migrations` (`~/.claude/skills/database-migrations/`) · `golang-patterns` (`~/.claude/skills/golang-patterns/`) · `golang-testing` (`~/.claude/skills/golang-testing/`) · `security-patterns` (`~/.claude/skills/security-patterns/`)

## Feature design

**State transitions**

```
queued ──▶ building ──▶ pushing ──▶ deploying ──▶ healthy
   │  └──────────rollback──────────▶ │            │
   │           │            │            │
   └───────────┴────────────┴────────────┴────▶ failed
   │           │            │            │
   └───────────┴────────────┴────────────┴────▶ cancelled
```

- A rollback deployment takes the shortcut arrow: `queued` to `deploying` to `healthy`. It never enters `building` or `pushing` because it re promotes a digest that already exists. That digest is copied from `source_release_id` at creation, so it is present before the deployment starts.
- `healthy`, `failed`, and `cancelled` are terminal. No transition leaves them.
- `cancelled` is reached only by supersession (a newer deployment for the same app) or an explicit cancel. It is not a failure and never reports one.
- `failed` always carries a `failure_reason`, including when the reconcile sweep fails a deployment whose build Job has vanished.
- Every arrow is one `deployment_events` row, written in the same transaction as the row update. So is the row's birth: `Create` writes an event with `from_state` null and `to_state` `queued`.
- `started_at` is set on the transition out of `queued`, and `finished_at` on the transition into any terminal state, both inside the same transaction as the event.

There is deliberately no public `CreateRelease`. A release only ever comes into existence through `MarkHealthy`, which owns the whole transaction: the row update, the event, the release insert (reading the digest from the deployment row, never from a caller), and the `apps.current_release_id` update. Making release creation reachable any other way would reintroduce the window where a healthy deployment has no release.

**Key invariants**

- Every state change is a database write before it is an action, and the row update plus its event row share one transaction (spec 0001).
- At most one non terminal deployment per app, enforced by a partial unique index, not by code.
- `state`, `build_path`, `outcome`, and `is_secret` accept only their enumerated values, enforced by CHECK constraints. Which transitions between states are legal is enforced in one Go function; the database enforces the values, Go enforces the moves.
- A `releases` row exists only for a deployment that reached `healthy`, at most one per deployment, and its `config_snapshot` and `image_digest` are never updated after insert. The only code path that creates one is `MarkHealthy`, so the row and its release are always written together or not at all.
- Every deployment is exactly one of a build deploy or a rollback, enforced by a CHECK on `upload_id` and `source_release_id`.
- `release_number` is contiguous and strictly increasing per app, and never reused, including after a rollback.
- A slug is globally unique across all app rows forever. A soft deleted app keeps its slug reserved.
- Nothing cascades. `foreign_keys=ON` with `ON DELETE RESTRICT` everywhere. The only hard deletion is the retention sweep, which deletes children before parents deliberately.
- `apps.current_release_id` always points at a release belonging to the same app, or is null.
- Domain and use case packages depend on the narrow store interfaces they define. They never import `internal/store` (project rule in `AGENTS.md`).

**Security model**

- Ownership is `apps.account_id`. Every app scoped read and write resolves the caller to an account through `api_tokens.token_hash` and then checks ownership. There are no roles and no sharing in the MVP; an account sees only its own apps.
- Tokens exist in the database only as a SHA-256 hash plus a non secret prefix. The raw token is returned once at mint time and never stored, logged, or recoverable. A disabled account, a revoked token, and an expired token are all indistinguishable to the caller.
- Upload fetch tokens are stored hashed and are single use, enforced by a conditional update rather than a read then write.
- Values in `app_config` marked `is_secret` are stored in clear. The database file sits on a volume mounted only by the control plane pod and already holds token hashes, so encrypting one column while the rest is readable buys little and adds a key whose loss destroys every app's configuration. The control is structural instead: `ConfigStore.ListForResponse` is the only read path any tool response may use and it never returns a secret value, while `ListForDeploy` is reachable only from the deploy path.
- Accept consciously that the exposure is wider than the live table. `releases.config_snapshot` copies secret values in clear, and releases are never pruned, so every past configuration of every app persists for the life of the database. Anyone who can read the volume, or any copy of it, reads all of it. This is the price of a rollback that restores the exact environment as well as the exact image, and it is the main reason any future backup decision has to treat this file as a secret store.
- `failure_reason` and `deployment_events.detail` are short sanitized strings. Raw build output stays in the build Job's pod logs and never enters the database.
- Every authorization outcome, allowed or denied, writes an `audit_log` row, including denials where the token resolved to nothing. Audit writes never block or alter the caller's response.
- No compliance regime applies. This is a single operator homelab platform holding no personal data.

**Configuration required**

- `DEPLOYER_RETENTION_DAYS`: how long `deployment_events` and terminal failed or cancelled deployments are kept before the sweep removes them. Default 90. Releases and the audit log ignore it and are kept indefinitely.
- `DEPLOYER_DB_BUSY_TIMEOUT_MS`: the SQLite busy timeout set at open. Default 5000.
- `DEPLOYER_POD_NAME`: the claiming pod's own name, injected by the Kubernetes downward API and recorded in `claimed_by`. Falls back to the hostname when unset, so a local run works.
- `DEPLOYER_DB_PATH` and `DEPLOYER_UPLOAD_DIR` already exist in spec 0001 and are unchanged.

**Critical test scenarios**

- Happy path: a deployment created from an upload walks `queued` to `building` to `pushing` to `deploying` to `healthy`, leaving five event rows in order, one release with `release_number` 1, and `apps.current_release_id` pointing at it. Verifies **AC-4**, **AC-5**, **AC-9**.
- Failure case, concurrency: two goroutines call `ClaimNext` against one queued row; exactly one gets it and the other gets zero rows. Verifies **AC-8**.
- Failure case, supersession: creating a second deployment for an app with one in flight cancels the first with reason `superseded`, writes its event row, and leaves exactly one non terminal row; a direct insert attempting a second non terminal row is rejected by the index. Verifies **AC-5**, **AC-7**.
- Failure case, torn release: `MarkHealthy` with a forced failure on the release insert leaves the deployment not `healthy`, no event row, and no release. There is no state in which a `healthy` deployment lacks a release. Verifies **AC-9**.
- Failure case, ambiguous source: inserting a deployment with both `upload_id` and `source_release_id`, and again with neither, is rejected by the CHECK constraint. Verifies **AC-16**.
- Failure case, illegal transition: a move from `healthy` to `building` is refused and writes no event row; a direct SQL update setting `state` to `pending` is rejected by the CHECK constraint. Verifies **AC-4**, **AC-6**.
- Failure case, rollback fidelity: a rollback against release 1 carries release 1's digest from creation, walks `queued` to `deploying` to `healthy` without entering `building` or `pushing`, and produces a release with the same digest, while `app_config` changed in between leaves release 1's snapshot untouched. Verifies **AC-10**.
- Failure case, slug retirement: create an app, soft delete it, create another with the same name, and confirm the second receives a different slug and the first slug is still taken. A forced suffix collision retries and succeeds. Verifies **AC-11**, **AC-12**.
- Failure case, referential integrity: deleting an app row with deployments present fails with a foreign key error. Verifies **AC-16**.
- Failure case, retention: with rows aged past the window, the sweep removes terminal failed deployments together with all their events including ones inside the window, removes standalone aged events of surviving deployments, removes redeemed uploads older than 24 hours, and leaves every release and audit row in place with no foreign key error. Verifies **AC-17**.
- Auth and permission: an unknown, revoked, or expired token resolves to no account and writes an `audit_log` row with `outcome = denied` and `account_id` null. Verifies **AC-13**, **AC-14**.
- Auth and permission: `ListForResponse` returns a non secret key with its value and a secret key with its name and flag but no value. Verifies **AC-15**.
- Migration: `goose up` then `goose down` on a fresh temporary file leaves it empty, and reopening confirms WAL, `foreign_keys`, and busy timeout are set. Verifies **AC-1**, **AC-2**, **AC-18**.

## Build plan

The whole model migrates in one file at step 2; what is staged is the query surface, not the schema.

## Consequences

**Positive**:

- Later slices add queries and behaviour, not schema. Slices 4, 7, and 8 never run a migration against live data on a database that has no backup.
- The invariants that matter most (one active deployment per app, valid states, permanent slugs, no orphans) are enforced by the database, so a stray query or a manual fix fails loudly rather than corrupting quietly.
- Diagnosing a stuck or failed deployment is one indexed scan of an ordered event log, which is exactly what an agent needs to be told what went wrong.
- A rollback restores the image and the environment together, so the thing that comes back is the system that was known healthy.
- The whole store is testable against a real SQLite file with no cluster and no mocks, which keeps the fastest feedback loop on the most load bearing code.

**Negative / tradeoffs**:

- Several tables sit empty for weeks. `api_tokens`, `app_config`, and `audit_log` are designed before the slices that use them are designed, so a later slice may still want a column added. The bet is that adding a column is cheap and reshaping relationships is not.
- Soft deleting apps means `deleted_at IS NULL` on the app read queries forever, and a query that forgets it shows a deleted app. The filter is narrow but it is real, and it is exactly the pollution soft deletes are usually criticised for.
- Secret configuration values are readable by anyone who can read the database file or a copy of it. The structural redaction protects tool responses and logs, not the file. Because every release snapshots them and releases are never pruned, the file accumulates every past secret of every app rather than only the current ones.
- `MarkHealthy` is a fat store method: it spans four writes across three tables. That is deliberate, since splitting it is what creates the torn state, but it is the one place the store does more than persist a single thing.
- Nine tables of `sqlc` queries plus their tests is a meaningful amount of code before the tracer bullet reaches a running app. Steps 1 to 7 are the critical path; steps 9 to 11 could slip behind slice 1 if the thread needs to land sooner.
- Everything about the platform now lives in one file with no backup. The blast radius of losing it grew from nothing to total the moment this migration runs.

**Neutral**:

- One new dependency, `oklog/ulid`.
- Ids are longer than integers and slightly larger on disk. At this platform's volume that is not measurable.
- `sqlc` generation becomes a step any schema change has to run, alongside `goose`. Both were already chosen in spec 0001.
- The seven state machine is more granular than slice 1 strictly needs. `pushing` and `cancelled` are unused until slices 2 and 6, but adding a state later means rewriting a transition table that other code branches on, so they are cheaper now than later.

## Follow-up

- [ ] Decide the backup and restore story for the platform database before relying on Deployer for anything you would mind losing. Spec 0001 raised it when the database was empty; this spec makes it the sole record of every app, owner, and running image. A restore rehearsal, not just a backup, is what closes it.
- [ ] Feature 4 (cluster foundation) is unspecced, and this schema assumes its naming: namespace `app-<slug>` and hostname `<slug>.$DEPLOYER_APP_DOMAIN`, both derived rather than stored. If feature 4 lands a different layout, the derivation moves but no column changes.
- [ ] Feature 8 (accounts and API tokens) owns token minting, hashing choice, and the prefix length. This spec fixes the columns and assumes SHA-256 and an 8 character prefix. Confirm both when that spec is written, before any token is minted in anger.
- [ ] Feature 11 (app environment configuration) owns the key naming rules. This spec fixes the CHECK as `key GLOB '[A-Z_][A-Z0-9_]*'` and reserves `PORT` for the platform. Confirm the reserved set there.
- [ ] Whatever backup decision follows must treat this database as a secret store, not just as metadata, because `releases.config_snapshot` retains every app's secret configuration for the life of the file. Encrypt the backup, or decide to exclude the snapshots and accept that a restored rollback loses its environment.
- [ ] `AGENTS.md` does not yet record the `oklog/ulid` dependency or the id prefix convention. Both are project wide and belong in root `AGENTS.md` once step 1 lands.
- [ ] Agent Skill and MCP discovery for `oklog/ulid` was declined. Record the decline in root `AGENTS.md` so it is not offered again.
