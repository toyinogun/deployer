## Summary

This adds `set_config`, `unset_config`, `get_config`, threads an optional `config` map through `deploy_app`, injects an app's configuration through one Kubernetes Secret plus a checksum annotation, and extends `get_logs` redaction to exact-match a caller's secret values. The domain validation, the store's transactional batch writes, the manifest composition, and the log redaction path are all careful and well tested — every acceptance criterion has a targeted unit test, and `/check verify` already exercised the whole thing against the real cluster (see `docs/specs/0010-app-environment-configuration/verify.md`). The one real problem is a race between when a deploy composes its Secret and when it snapshots the release: `MarkHealthy` re-reads live configuration rather than using the configuration the deploy actually composed with, so a `set_config` landing during the readiness wait produces a release snapshot that does not match what the running pod received, contradicting AC-10 and undermining the future rollback slice that depends on it.

## Major

### 🟠 The release snapshot can record configuration the deploy never actually ran with, `internal/reconcile/reconcile.go:610` and `internal/store/deployments.go:302`
**Problem**: `deployApp` reads the app's configuration once (`internal/reconcile/reconcile.go:613`, `config, err := r.apps.ConfigForDeploy(...)`) and uses that single read to compose both the Secret (`deploy.Secret(in)`, line 637) and the pod template checksum (`deploy.ConfigChecksum` via `deploy.Deployment(in)`, line 640). The comment directly above (lines 610-612) states the intent explicitly: "Read once, here, so the Secret the container is given, the checksum on its pod template, and the release snapshot all describe the same configuration." But the release snapshot is not built from that same `config` value. `MarkHealthy` (`internal/reconcile/reconcile.go:647`) takes only a deployment id, and inside the store (`internal/store/deployments.go:302`, `configSnapshot(ctx, q, current.AppID)`) it independently re-queries `ListConfigForDeploy` at whatever moment `MarkHealthy` happens to run — which is after `awaitReady` (line 644), i.e. after however many reconcile ticks the app took to become ready. A `set_config` call landing in that window is included in the snapshot even though the Secret the running pod actually reads from was written before that call, and `envFrom` does not update a running container's environment without a pod restart.
**Why it matters**: This breaks AC-10 ("The release cut when a deploy becomes healthy snapshots the configuration that deploy actually ran with") for any configuration change that happens to land between compose and health. It is also exactly the data the spec's own follow-up section says slice 8's rollback will trust to restore an app's Secret ("Slice 8's rollback must rewrite the app's Secret from the release snapshot... not only re promote the image digest"). A rollback built on a snapshot that can silently diverge from what the pod actually ran with will roll a Secret to values the rolled-back release never used, in the one place the whole feature promises fidelity.
**Suggested fix**: Thread the `config` map already read in `deployApp` through to `MarkHealthy` (e.g. accept it as a parameter, or have the caller pass the already-marshalled snapshot JSON) instead of having `configSnapshot` re-query the store independently. This also removes the now-inaccurate half of the comment at `reconcile.go:610-612`. Worth a regression test in `internal/store/lifecycle_test.go` or `internal/reconcile/config_test.go` that calls `SetConfigBatch` between compose and `MarkHealthy` and asserts the release snapshot reflects the pre-change value.

## Minor

None beyond the one gap noted above; the store, domain, and MCP layers are otherwise well covered.

## Strengths

- The secret-flag-required rule (AC-16) and its `omitempty` schema workaround (`internal/mcp/config.go:74-87`) are exactly right, and `internal/mcp/wire_test.go` pins the failure mode (schema rejecting before the domain rule runs) that bit the earlier verify pass — a good example of a real bug becoming a permanent regression test.
- Log redaction's rotation handling (`secretLiterals` unioning current secret values with the running release's snapshot, `internal/mcp/logs.go:196-222`) is correct and has a dedicated test for the rotated case, the short-secret case, and the flipped-to-plain case, matching the spec's stated hole exactly.
- The two-method split in the store (`ListConfigForResponse` vs `ListConfigForDeploy`) pushes the secrecy decision into SQL rather than Go, and `internal/store/config_test.go` proves it at that layer rather than trusting a caller above it to withhold correctly.

## Test coverage

Coverage is strong and specific: `internal/domain/config_test.go` covers every `ValidateConfig` branch including the bound edges and duplicate-key case; `internal/store/config_test.go` covers the transactional batch write/unset and the response-vs-deploy read split; `internal/deploy/config_test.go` covers the Secret composition, the checksum's order-independence and collision-avoidance, and AC-15's empty-value case; `internal/mcp/redaction_test.go` covers all four AC-11 scenarios; `internal/build/noconfig_test.go` pins AC-14 with both a reflection check on `build.Input` and a check of composed build pods. The one gap is the MarkHealthy/config-snapshot race above — no test (unit or the `/check verify` pass) exercises a configuration write landing between compose and healthy within a single deploy, which is exactly the scenario that exposes the bug.
