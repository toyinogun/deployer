# Review, main, 2026-08-12 (first deploy end to end)

**Reviewed by**: Claude Sonnet 5 (author on unknown/prior session)
**Scope**: 78 files, bf84aa8..HEAD (branch-equivalent, main)
**Verdict**: Changes requested

## Summary

This range wires spec 0004 end to end: the upload endpoint and hardened tar extractor, the Buildpacks build Job and registry client, app namespace and workload composition over a real client-go clientset, the reconcile loop from `queued` to `healthy`, the MCP `deploy_app` tool and its auth middleware, and the surrounding config, store adapters, and cluster manifests. The security-critical surfaces are genuinely careful: `internal/source`'s extractor refuses symlinks, hardlinks, absolute paths, `..` climbs, duplicate paths, and both a per-file and total size cap; `internal/uploads` never lets a caller choose a filesystem path; the registry push credential is scoped, owner-referenced to its Job, and never reaches an app container; every manifest in `internal/build` and `internal/deploy` is composed field by field with no caller string anywhere near a pod spec. Test coverage across the range is broad and mostly excellent, including hostile-archive and no-caller-value-in-pod-spec tests that specifically defend the invariants AGENTS.md calls load bearing. The two real gaps are that the build pod's `runAsUser`/`runAsGroup` are hardcoded Go constants rather than read from the pinned builder image — directly against the rule this range itself added to AGENTS.md, and one the team has already been bitten by once — and that the reconcile loop's three-way timeout attribution (`AC-17`, `deploy` vs `build` vs `ready` budgets) has no unit test, despite being explicitly named a critical test scenario in the spec.

## Major

### 🟠 The build pod's uid/gid are hardcoded, not read from the pinned image, `internal/build/job.go:39`
**Problem**: `buildUID = int64(1001)` and `buildGID = int64(1000)` are Go constants baked into `job.go` and forced onto the pod via `RunAsUser`/`RunAsGroup`/`FSGroup` in `podSecurity()` and onto every container via `containerSecurity()`. The comment directly above them says "read from the pinned builder's own image config rather than assumed," but nothing in this range reads them from the image at runtime — they were read once by a human and committed as literals. `internal/build/job_test.go:95-101` makes the history explicit: a prior version started the pod at `1000:1000`, every unit test passed (the fake clientset execs nothing), and every real build died with `failed to exec as user 1001:1000: operation not permitted`. The fix that shipped was to hardcode the correct value rather than to read it from the image.
**Why it matters**: This is the exact failure mode AGENTS.md's newly-added invariant exists to prevent: "the build pod runs as the builder image's declared `CNB_USER_ID`... Read those uids from the pinned images, never assume them." `DEPLOYER_BUILDER_IMAGE` is validated only for being digest-pinned (`internal/config/firstdeploy.go:91`), not for having uid 1001:1000. The moment that digest is repinned to a newer Paketo `jammy-base` build whose `cnb` user differs, every build fails with the same permission error this range already hit once, and no test in the suite — unit or otherwise — will catch it before a real deploy does, because `job_test.go` pins the same hardcoded value it is meant to be checking.
**Suggested fix**: Read `USER`/`CNB_USER_ID` off `DEPLOYER_BUILDER_IMAGE`'s config blob the same way `internal/registry.ImageUser` already reads it off a pushed app image, either at startup (failing boot if it cannot be resolved, consistent with "every `DEPLOYER_*` variable is validated... never at first use") or by making it a configuration value validated the way the image digest is. Short of that, leave a loud `/check verify` step that fails when the builder digest changes without a corresponding uid re-check, so the drift is caught before it reaches a real build.

### 🟠 The reconcile loop's timeout attribution (AC-17) has no unit test, `internal/reconcile/reconcile.go:428`
**Problem**: `wait` is the function that decides which of `timeout`, `build_failed`, or `app_never_ready` a deployment fails with, by comparing the outer deploy-budget context against the inner phase context (`buildCtx` in `awaitBuild`, `readyCtx` in `awaitReady`). It is genuinely subtle: it has to distinguish "the build's own deadline passed while the overall deploy still had budget" from "the overall deploy budget ran out while the build was still within its own deadline," and route each to a different reason code. `internal/reconcile/reconcile_test.go` never exercises either path — there is no test that lets `BuildTimeout` or `ReadyTimeout` actually expire, and no test asserting `domain.ReasonTimeout` or `domain.ReasonAppNeverReady` at all.
**Why it matters**: The spec's own "Critical test scenarios" list names this directly: "Failure case, never ready: a Deployment that never reports an available replica fails with `app_never_ready` after `DEPLOYER_READY_TIMEOUT_SECONDS`. Verifies AC-16, AC-17." Under `TESTS = configured`, branching logic this load-bearing (it is the whole implementation of AC-17) being untested is a Major finding on its own; that the spec explicitly called out the scenario and it still shipped without a test raises it further. `docs/specs/0004.../verify.md` proves the three timeouts fire correctly against a real cluster, which is good, but that is a one-time manual run, not a regression net — a future change to `wait`'s branch order would pass CI with nothing catching it.
**Suggested fix**: Add a test that gives `awaitBuild` a `Cluster` fake whose `JobState` always returns `JobRunning`, with `BuildTimeout` set short and `DeployTimeout` set longer, and assert the deployment ends `failed` with `build_failed`; mirror it for `awaitReady`/`app_never_ready` with `WorkloadReady` always false; add a third where `DeployTimeout` itself is the shorter budget and assert `timeout` wins over the phase-specific reason.

## Minor

### 🟡 `awaitBuild`'s inner loop can double-fail past its own deadline under a busy API server, `internal/reconcile/reconcile.go:320`
**Problem**: On a `JobState` error, the loop logs and falls into `case err != nil:` (a no-op case), then calls `r.wait`, which sleeps for `ReconcileInterval` or until `buildCtx` is done, whichever comes first. If the Kubernetes API is erroring repeatedly right up to the build deadline, the last few ticks each cost a full `ReconcileInterval` on top of API latency, so the effective deadline for reporting `build_failed` can run a little past `DEPLOYER_BUILD_TIMEOUT_SECONDS`. Bounded by `DeployTimeout` either way, so it cannot hang the call, but the phase-specific budget is softer than the config value promises.
**Why it matters**: Low practical impact — it is capped by the outer deploy timeout and self-corrects on the next tick — but it is worth knowing the "build phase at `DEPLOYER_BUILD_TIMEOUT_SECONDS`" claim in AC-17 has a small amount of slack when the Kubernetes API itself is degraded, which is exactly when a caller most wants an accurate signal.
**Suggested fix**: Optional. If it matters later, have the `err != nil` branch skip the `ReconcileInterval` sleep and retry immediately (bounded by a short backoff), so a wedged API server does not silently borrow time from the phase budget.

### 🟡 `registryHost` assumes the target image reference always has a `/`, `internal/build/job.go:225`
**Problem**: `registryHost(image string) string` scans for the first `/` and returns everything before it, falling back to the whole string if none is found. `TargetImage` (`internal/build/credential.go:79`) always produces `host/apps/slug:id`, so in practice this never hits the fallback, but the function is exported-shaped (lowercase but used across the package) with no doc comment explaining the "falls back to the whole string" behavior is dead code given its only caller, which reads as an unhandled case to a reader who does not already know `TargetImage`'s shape.
**Why it matters**: Not a live bug today, but it is the kind of implicit coupling ("this is safe only because the one caller always includes a slash") that AGENTS.md's doc-comment rule exists to make explicit, and a future caller with a bare-host image reference would silently get `CNB_INSECURE_REGISTRIES` set to the full reference rather than just the host.
**Suggested fix**: A one-line comment noting the invariant it relies on (`TargetImage` always contains at least one `/`), or an explicit error/panic on the no-slash case rather than a silent fallback.

## Nits

- ⚪ `internal/build/job.go:73`, `JobName` and `SecretName` are identical (`"build-" + objectNameFor(id)`), which is deliberate collision as documented at `credential.go:65` (owner reference cleanup), but a reader hitting `JobName` first has no pointer forward to that reasoning until they reach `SecretName`.
- ⚪ `internal/registry/registry.go:213`, `repoPath`'s heuristic for stripping a leading host (`strings.ContainsAny(host, ".:")`) would treat a bare `localhost` repo segment as a path component rather than a host, but the platform's own `repoPath` calls are always full `host:port/apps/slug` references, so this is unreachable in practice.
- ⚪ `internal/mcp/mcp.go:280`, `deny`'s `cause error` parameter is `nil` in the `checkUpload`/`resolveApp`-failure calls that pass a real error, and non-nil elsewhere; the mix reads fine but a doc comment on why some call sites pass `nil` (validation failures with nothing to log) versus real errors would save a reader tracing both call sites.

## Strengths

- `internal/source.Extract` is exemplary hardening: absolute paths, `..` components, backslashes and colons, symlinks/hardlinks/devices, duplicate paths (`O_EXCL`), a hard entry-count cap, and a per-file-and-cumulative byte cap that stops one byte past the limit rather than after a full write — and `extract_test.go` has a dedicated test for nearly every one of those refusals plus a "stops at the first refusal" test proving no partial tree survives a rejection.
- `internal/deploy/deploy_test.go:191`'s `TestNoCallerSuppliedValueReachesThePodSpec` and the parallel golden tests in `internal/build/job_test.go` directly test the load-bearing "no user-supplied value in a pod spec" invariant rather than just asserting the manifests look right, which is exactly the kind of test that would have caught a regression here.
- The reason-code boundary (`domain.Reason`, `toolError` in `mcp.go`, `fail` in `reconcile.go`) is airtight: every failure path funnels through one of nine closed codes and a canned message, build output and wrapped errors are logged server-side only, and `mcp/deploy_test.go:188`'s `TestAFailedDeployReportsTheCodeAndNothingElse` proves it end to end.
- The app `Deployment`'s container `SecurityContext` deliberately omits `RunAsUser` (`internal/deploy/deploy.go:221`), correctly leaving the run image's own declared user in force rather than assuming one — the right call, in contrast to the build pod's hardcoded uid flagged above.

## Test coverage

Coverage across this range is broad: `internal/source`, `internal/uploads`, `internal/auth`, `internal/build`, `internal/deploy`, `internal/registry`, `internal/config/firstdeploy.go`, `internal/store`'s new adapters, and the MCP tool/middleware pair all have thorough table-driven and scenario-based tests, including the hostile-archive, no-caller-value-in-pod-spec, bootstrap-idempotency, and audit-denial cases the spec calls out as critical scenarios. The two gaps are the ones named above: `internal/reconcile`'s AC-17 timeout-attribution branches (`build_failed`-by-deadline, `app_never_ready`, and overall `timeout` all lack a unit test), and the build pod's hardcoded uid has no test capable of catching drift against a repinned builder image, a known limitation of the fake clientset that AGENTS.md itself now documents and that this specific value already broke real builds once before being hardcoded around rather than fixed at the source.
