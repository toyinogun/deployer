## Summary

This extends the existing account disable into a full suspension: an admin action now scales an account's live apps to zero, restore scales them back with no rebuild, a sweep holds suspended accounts at zero on the reconcile cadence, an in-flight deployment is ended at the next phase boundary, and every MCP tool call and upload from a suspended account's token is refused with the closed reason code `account_suspended`. The implementation is unusually thorough for a first pass: the spec's own verify log shows three real defects (the `Forbidden`-vs-`NotFound` namespace case, the mid-build suspension window, and the restore message wording) found on the real cluster and fixed with regression tests before this review, which is exactly the debug-then-pin loop the project asks for. `go build`, `go vet`, `golangci-lint run`, `gofmt -l`, and `go test -race` across every touched package are all clean as of this diff. The design correctly threads the suspension state through the one place it lives (`accounts.disabled_at`), keeps the cluster half best-effort behind a database write that lands first, and reuses `deploy.ServingReplicas`/`deploy.NamespaceName`/`deploy.WorkloadName` rather than re-deriving any of them. Both admin surfaces genuinely share one use case (`internal/suspend`), and the MCP refusal is registered once above every tool rather than per tool. The two items below are minor and neither blocks merge.

## Minor

### 🟡 A restore that fails to enumerate apps leaves them stranded with no retry path, `internal/suspend/suspend.go:79`
**Problem**: `set()` writes the lockout, records the account audit row, and only then calls `s.apps.DeployedAppsByAccount(ctx, accountID)`. If that read itself fails (a store/context error, as opposed to an individual `ScaleWorkload` failure), the function returns `Result{}, err` before ever reaching the per-app loop. On suspend this is recoverable: the account is already locked out and the sweep (`SweepSuspended`) will pick the apps up on its next tick regardless of whether this call ever listed them. On restore it is not: by AC-8 and the sweep's own doc comment, nothing but this code path ever scales an app up, so an app that was never reached because the app list itself failed to load stays at zero replicas indefinitely, with no sweep, no timer, and nothing surfaced to the admin beyond a generic error — even though the account row was already flipped back to active.
**Why it matters**: The admin sees a failure response and has every reason to believe nothing happened, when in fact the account is unsuspended and its apps are silently stuck down. A retry of "Restore" from the page or JSON route is idempotent and would very likely fix it (since it starts from `SetDisabled` again and re-reads apps), so this is not catastrophic, but it is a real gap in the "third outcome" (`NotStopped`) that AC-6 otherwise handles carefully for the per-app case — the app-enumeration failure isn't given the same treatment.
**Suggested fix**: Either treat a `DeployedAppsByAccount` error on the restore path as itself producing a `NotStopped`-shaped signal the caller can act on (even if it can't name individual apps), or note in the use case's doc comment that this specific failure mode is an accepted gap distinct from the per-app one, so a future reader doesn't assume AC-6 covers it.

## Nits

- ⚪ `internal/suspend/suspend.go:39,151`: `Result.Stopped` is populated on every successful scale but never read by any caller or test (only `Result.NotStopped` is consumed by the admin page, the JSON route, and the test suite). Either drop the field or use it — it's currently a bit of bookkeeping nothing acts on.

## Strengths

- The three defects the branch's own `/check verify` runs found on the real cluster (forbidden-vs-not-found for a vanished namespace, the mid-build suspension window in `awaitBuild`/`awaitReady`, and the wrong restore-retry copy) were each turned into a targeted regression test (`TestScaleWorkloadTreatsAVanishedNamespaceAsSuccess`, `TestASuspensionDuringABuildThatIsStillRunningEndsTheDeployment`, `TestAPartialRestoreNeverPromisesARetry`) rather than just patched, which is exactly the loop `internal/reconcile/stranded_test.go`'s convention asks the codebase to follow.
- `internal/mcp/middleware.go`'s refusal is proved through `Server.Handler()` over `httptest`, not `callOverTheWire`, precisely because AC-10 calls out that the latter skips the authentication middleware this feature changes — the test suite in `internal/mcp/suspension_test.go` sweeps every tool by name rather than a sample, so a tool added later without updating the list would still be caught by the "every tool inherits the refusal" claim.
- `internal/kube/kube.go`'s `ScaleWorkload`/`namespaceGone` pair correctly distinguishes "the namespace is gone" from "the RoleBinding inside a namespace that still exists is broken" — collapsing those would have silently reported apps as stopped when they were not, which is the one failure mode AC-6's audit trail exists to prevent.
- The sweep's `AccountSuspended` re-read immediately before each write, rather than trusting the snapshot list, is tested with a genuinely deterministic race (`TestARestoreInsideASweepSurvivesIt` restores from inside the fake scaler's callback, at the exact moment between the list and the write) rather than a sleep-based approximation.
- `internal/reconcile`'s `blocked`/`wait` change correctly moves the suspension check into the per-tick poll loop rather than only at phase boundaries, with a test (`TestASuspensionDuringABuildThatIsStillRunningEndsTheDeployment`) that specifically exercises the window between phase boundaries where the original bug lived.

## Test coverage

Coverage is thorough and follows the project's test conventions: table-driven credential-shape tests in `internal/auth`, a real SQLite store in `internal/suspend` and `internal/store` rather than a faked one, the `client-go` fake clientset for `internal/kube` and `internal/reconcile`, and the real-HTTP-handler path for the MCP refusal per AC-10's own requirement. Every acceptance criterion in the spec has at least one test cited against it in a `covers:` comment, and the spec's `verify.md` records a second pass against the real cluster that closed the gaps a fake clientset structurally cannot reach (RBAC-driven `Forbidden` on a deleted namespace, real build timing). The one edge case not covered by a test is the restore-enumeration failure mode described in the Minor finding above, which is a real gap but a narrow one.
