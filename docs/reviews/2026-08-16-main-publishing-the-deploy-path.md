## Summary

Spec 0022 publishes the MCP and upload endpoints on a third public hostname, `mcp.deploy.toyintest.org`, replacing what the tailnet was silently providing with a stated set of controls: a 90 MB upload ceiling under Cloudflare's cap, a per-address token bucket, a bad-token lockout living once in `auth.Authenticator`, a per-account unclaimed-upload cap enforced inside the same transaction as the insert, an expiry sweep, and a widened `CF-Connecting-IP` trust set. `DEPLOYER_PUBLIC_URL` is removed outright and replaced by two derived addresses, `ConsoleURL` and `MCPURL`, each owned by exactly one hostname setting. The change also fixes a real production incident found mid-build: removing `DEPLOYER_PUBLIC_URL` collapsed the accepted CSRF origin set to one entry and made every page POST on the tailnet console answer 403, fixed by `acceptedOrigin`'s same-origin comparison. The build plan, the verify checklist, and the acceptance criteria all line up with what shipped, the closed reason-code set was audited and repaired (six codes that had escaped `theSet` are now pinned), and the tunnel rule ordering, network policy no-new-peer claim, and route registration shape are all backed by tests that read structure by name/shape rather than by position — directly addressing the class of bug (the shadowed console rule) that bit this same codebase in spec 0021. This is careful, disciplined work with unusually good test coverage of the exact properties the spec cares about (AC-2 through AC-19 all have a directly corresponding test). I found no blockers. A few minor items below are worth a look, mostly around residual references to the old `DEPLOYER_PUBLIC_URL` shape in the identity package's `PublicURL` field name and a couple of small robustness/consistency points that don't affect correctness of the shipped behavior.

## Minor

### 🟡 `identity.Options.PublicURL` field name no longer matches what it holds, `internal/identity/service.go:115-118`
**Problem**: `Options.PublicURL` is now always fed `cfg.ConsoleURL` (see `cmd/deployer/main.go:211`: `identity.Options{PublicURL: cfg.ConsoleURL}`), but the field is still named `PublicURL` and its doc comment says "the base address a mailed link points at" without naming which of the two public surfaces that is.
**Why it matters**: The whole point of this spec is that there are now two derived public addresses and they must not be confused; a field called `PublicURL` reads as if it could still be either one, and a future caller wiring `MCPURL` in here by mistake would compile cleanly and silently put the deploy host into verification/reset/invite links.
**Suggested fix**: Rename the field to `ConsoleURL` (matching the `web.Options.ConsoleURL` and `httpapi.NewIdentity(..., consoleURL, ...)` naming already used elsewhere in this same commit) so the type system documents the invariant the comment states in prose.

### 🟡 `a.address(r)` recomputed up to four times per request, `internal/httpapi/httpapi.go:127-181`
**Problem**: `createUpload` calls `a.address(r)` on nearly every branch (rate limit check, authenticate call, suspended-account denial, too-many-attempts denial, generic denial, success path) instead of computing it once at the top of the handler. `internal/mcp/middleware.go`'s `authenticate` has the same shape but only calls `s.address(r)` twice, which is more defensible.
**Why it matters**: `auth.ClientAddress` re-parses headers and does string work on every call; it's cheap per call but this is the hot path for every upload, and the repetition is also a maintainability smell — a future edit to one call site's argument (e.g. adding another trusted host list) risks drifting from the others even though they're meant to always agree.
**Suggested fix**: Compute `addr := a.address(r)` once at the top of `createUpload` and thread it through, the way `deployPathHarness` in `mcp_test.go` and `denyTransport` already take `addr` as a parameter rather than recomputing it.

### 🟡 `internal/mcp/mcp.go`'s `New` silently falls back to a private limiter that bypasses the authenticator's lockout, `internal/mcp/mcp.go:252-256`
**Problem**: When `opts.Limiter` is nil, `New` builds a fresh `identity.NewLimiter(...)` for the token bucket, but `WithLockout` on the shared `auth.Authenticator` is wired separately in `cmd/deployer/main.go` from the *same* `deployLimiter` instance passed to both `mcp.New` and `httpapi.New`. If a future caller constructs an `mcp.Server` without passing `Limiter` (as `deploy_test.go`/`logs_test.go`'s harnesses apparently do, based on the diff context), the token bucket is bounded but the authenticator's lockout — which is a *different* `Limiter` instance set via `WithLockout` at construction time — is not connected to it. That's expected and by design (the lockout is inside `auth.Authenticator`, not this package), but the fallback creates a second, unrelated `Limiter` whose only purpose is the token bucket, and nothing documents that this fallback path never exercises AC-16's cross-route lockout guarantee.
**Why it matters**: Low risk in production, since `main.go` always wires the same instance to both `Options.Limiter` and `WithLockout`. But a test harness that omits `Limiter` (relying on the fallback) is testing a limiter no other code path shares, which is exactly the kind of quiet drift the AGENTS.md rule about `deployPathHarness` needing both routes on one limiter is meant to catch.
**Suggested fix**: No code change needed if every test harness that exercises AC-16 already builds its own shared `Limiter` and passes it explicitly (which `deployPathHarness` in `lockout_test.go` does correctly). Worth a one-line comment on the fallback in `mcp.go` noting that a caller relying on it gets no shared lockout, so a future test author doesn't assume the fallback is equivalent to production wiring.

## Strengths

- The regression class from spec 0021 (a positionally-correct-looking but semantically shadowed tunnel rule) is directly guarded against here: `tunnel_test.go`'s `tunnelRules` helper reads rules by hostname/shape rather than index, and the AGENTS.md file explains *why* in enough detail that a future editor won't reintroduce the bug by "simplifying" the test back to index-based assertions.
- `TestABadTokenRunLocksBothDeployRoutes` in `internal/mcp/lockout_test.go` is a genuinely strong test: it spends the entire failure budget on one route (`/v1/uploads`) and asserts the *other* route (`/mcp`) is locked out too, which is the only way to actually prove the lockout lives in `auth.Authenticator` rather than being duplicated per-handler — exactly the kind of test the root AGENTS.md calls out as necessary after the 2026-08-16 sign-in lockout incident.
- The mid-build discovery and fix of the tailnet console CSRF regression (commit `f7ce040`) is handled the right way: root-caused (`DEPLOYER_PUBLIC_URL` removal collapsed the accepted-origin set to one), fixed with a same-origin comparison rather than a hardcoded list, documented in both the spec's "Narrowed by" section and a dedicated test (`TestAPostIsAcceptedFromTheConsoleAndFromItsOwnNameAndNoOther`) whose docstring explicitly explains why the *previous* test passed despite testing nothing new.
- `internal/domain/closedsets_test.go` closes a real gap (the closed `domain.Reason` and `identity.Code` sets could previously have collided in string value with nothing to notice) and does it by comparing actual values rather than trusting a comment.

## Test coverage

Strong and squarely targeted at the acceptance criteria. Every AC from 0022 that the unit suite is supposed to hold (per `verify.md`'s own claim) has a directly corresponding test I could find: host-qualified registration and its catch-all (`deployhost_test.go`), tunnel rule order and count (`tunnel_test.go`), config validation for `DEPLOYER_MCP_HOST`/`DEPLOYER_PUBLIC_URL` (`edge_test.go`), the two size gates (`TestAnOversizedBodyIsRefusedWithAClosedCode`), the unclaimed-upload cap and its no-bytes-on-refusal property, the sweep's referenced-vs-unreferenced split, the cross-route lockout, the two-host `CF-Connecting-IP` trust boundary (`trustedhosts_test.go`), and the closed reason-code set repair. The project's own rule that an MCP handler test must cross the wire to prove a reason code reaches a caller is respected for the cases that need it: the lockout test drives real HTTP through `httptest.Server` rather than calling handler methods directly, which is the same bar `wire_test.go`'s `callOverTheWire` sets. I did not find any new branching/security-relevant logic left untested; the manual-only items (AC-1, AC-20, and the DNS/live-timing verify.md rows) are correctly left to `/check verify` rather than faked into the unit suite.
