# Review, feat/stranded-deployment-recovery, 2026-08-14

**Reviewed by**: Claude Sonnet 5 (author on Claude Sonnet 5)
**Scope**: 12 files, branch vs main (merge base `cb9314d`)
**Verdict**: Changes requested

## Summary

The change widens `ClaimNext` to fall back to the oldest unclaimed non-terminal row, adds a conditional `ReleaseBuildingClaim` write, and adds `recoverStranded`, a check that asks the cluster what a `building` row's Job actually did before the budget pass runs. The store layer is clean: the conditional release, the widened claim query, and their tests correctly prove the ordering, the fairness, and the supersession race the spec calls out (AC-5, AC-5a). The problem is with `recoverStranded` itself: given this package's single-goroutine, panic-crashes-the-process concurrency model, there is no live-process code path that leaves a `building` row un-driven other than a `Transition` write failing inside `fail()`. The scenario the spec's summary, AC-1, and its own `verify.md` describe — kill a build Job mid build and watch the row get caught within a tick or two — is what `Sweep` already resolves synchronously on every restart, before `Tick` (and therefore `recoverStranded`) ever runs. The two unchecked boxes in `docs/specs/0014-stranded-deployment-recovery/verify.md` for exactly that scenario are consistent with this: it was tried on the real cluster and could not be observed working as described.

## Blockers

### 🔴 `recoverStranded`'s primary scenario is resolved by `Sweep` before `Tick` ever sees it, `internal/reconcile/reconcile.go:309-401`
**Problem**: The whole feature is framed, in the spec's Summary, AC-1, AC-2, and the build plan's verify step 6, around one story: a deploy's drive dies (the build pod's process ends, or the goroutine driving it stops), and the row is noticed and ended within seconds rather than at the ten-minute budget. But `Drive` is only ever called synchronously from `Tick` or `Sweep`, both on the one goroutine `Run` starts (`cmd/deployer/main.go:271`, `go loop.Run(ctx)`, no `recover()` anywhere in the call chain). In this model, a panic in `Drive` is unrecovered and kills the whole process — which triggers a pod restart, and `Run` calls `r.Sweep(ctx)` (line 280) *before* the ticker loop that calls `Tick` ever starts. `Sweep` calls `Drive` directly on every non-terminal row, and `Drive`'s own `awaitBuild` (lines 687-713) makes the exact same `JobFailed`/`JobGone`/`JobSucceeded` decision `recoverStranded` makes, synchronously, before `recoverStranded` gets a chance to run at all. If the process does *not* restart, then whatever goroutine claimed the row is still inside `Drive`/`awaitBuild`, which polls the Job itself every `ReconcileInterval` and reaches the same true reason on its own — again without `recoverStranded`'s help. The only reachable case where a `building` row sits un-driven while the process stays up is a `Transition` write failing inside `fail()` (line 919) after the reason was already computed — a real but much narrower case than "a drive died."
**Why it matters**: This is the reason the spec exists (`docs/specs/0014-stranded-deployment-recovery/index.md:8`, "the only thing that eventually ends it is the deploy budget... even when the build pod failed and said so minutes earlier"). `verify.md`'s two cluster steps for exactly this scenario are unchecked: "kill a build Job mid build → within a tick or two `get_status` reports `build_failed`" and "kill the control plane pod mid build, let it restart... watch the row" — both `[ ]`, and the extra runtime context for this review states `recoverStranded` could not be triggered on the live cluster for exactly the reason above. Shipping this as "done" (scope.md marks the build checklist `[x]`) means an operator reading spec 0014 believes a stranded row is now caught within seconds, when in the tested restart scenario it is actually `Sweep` catching it — a pre-existing mechanism this PR did not need to add `recoverStranded` for — and in the no-restart scenario it is `awaitBuild`'s own poll loop catching it, also pre-existing.
**Suggested fix**: Either (a) find and document the actual live-process scenario where a `building` row is claimed but nothing is driving it — if it is genuinely limited to a `fail()` write failure, narrow the spec's claims and the code's comments to that case rather than "a drive that died," or (b) if the intent really is to shorten the restart-recovery path, recognize that `Sweep` already provides it synchronously and this feature's marginal value is smaller than advertised. Either way, check the two unchecked `verify.md` cluster boxes against the real cluster (kill the Job without restarting the pod, and separately with a restart) and record what actually happens before marking the spec `in-progress` item's Build/Verify boxes done.

## Major

### 🟠 `docs/scope/scope.md` marks Build and several checklist items `[x]` while `Verify it` stays `[ ]` and the underlying verify steps are unchecked, `docs/scope/scope.md:305-312`
**Problem**: The diff flips `- [ ] Build it` to `- [x] Build it`, plus all four sub-bullets, based on the fake-clientset test suite passing. But two of the `verify.md` cluster steps this build plan explicitly deferred to `/check verify` (the killed-Job step and the restart-while-building step, which are the two steps that actually exercise `recoverStranded`'s reason for existing) are unchecked, and per the runtime context for this review, attempting them showed the mechanism doesn't trigger as designed.
**Why it matters**: A reader of `scope.md` sees a fully checked Build section for a feature whose central behavior was not confirmed to work, and whose one attempt to confirm it surfaced the gap described above. That is exactly the kind of drift `/sync` and `/check verify` exist to prevent.
**Suggested fix**: Leave the build checklist unchecked (or add a caveat) until the `Verify it` pass runs and the cluster steps are resolved one way or the other, and update the language in the spec and scope entry to match whatever `recoverStranded`'s real trigger conditions turn out to be.

## Minor

### 🟡 `ReleaseBuildingClaim`'s affected-row count is discarded, `internal/store/deployments.go:465-473`
**Problem**: `s.q.ReleaseBuildingClaim` returns `(int64, error)` (an `:execrows` query), and `Store.ReleaseBuildingClaim` discards the count entirely, only checking the query `error`. A `WHERE id = @id AND state = 'building'` update that matches zero rows (the AC-5a supersession case) is indistinguishable, at this layer, from one that matched exactly one row — both return `nil` error.
**Why it matters**: This is almost certainly intentional per AC-5b ("a release write that fails changes nothing and is not retried"), and the caller (`recoverStranded`) does log success unconditionally regardless of whether a row was actually released, which is a little misleading (`internal/reconcile/reconcile.go:394`, "handed a stranded deployment back to be resumed" logs even when the guard silently no-opped because a supersession beat it there). Not a correctness bug, but the log line overstates what happened in the race case, which is exactly the case worth being able to see in production logs.
**Suggested fix**: Either have `ReleaseClaim`/`ReleaseBuildingClaim` surface whether a row was actually released (return the count or a bool), and log the no-op case distinctly ("claim not released: the row was no longer building"), or adjust the log wording to something that is true whether or not the write mattered.

## Nits

- ⚪ `docs/specs/0014-stranded-deployment-recovery/verify.md`, the acceptance-criteria coverage line at the bottom cites AC-1 as covered "by the killed Job step and the test command," but the killed Job step is unchecked — worth a footnote distinguishing "covered in principle" from "confirmed."

## Strengths

- The store layer is exactly right: `ReleaseBuildingClaim`'s guard (`state = 'building'`) directly protects the AC-5a race, and `store/claim_test.go`'s `TestReleasingAClaimOnARowSomethingElseEndedWritesNothing` and `TestQueuedWorkIsClaimedAheadOfAnOlderStrandedRow` prove the exact invariants the spec calls out (clearing `claimed_at` specifically, not just `claimed_by`; queued work never overtaken).
- `Tick` sharing one `ListNonTerminal` read between `recoverStranded` and `expireOverdue`, and running recovery first, correctly satisfies AC-1's "no extra store round trip" and AC-6's "true reason beats timeout" — and `TestAStrandedAndOverdueRowIsEndedWithTheTrueReasonNotTimeout` pins the ordering rather than assuming it.
- The `build.JobState` switch in `recoverStranded` is written as an exhaustive four-arm switch with no default, matching the spec's decision table one-for-one, and the `deploy/AGENTS.md` addition correctly documents `replicas: 1` / `Recreate` as now load-bearing for this check rather than leaving that invariant implicit.

## Test coverage

Every branch the spec's Critical test scenarios ask for is covered against the fake clientset and a real SQLite store: failed, gone, succeeded, running, unreadable, the stranded-and-overdue ordering, the keeps-stranding budget case, and the store-level release/adopt/fairness/race set. That is a genuinely thorough unit suite. What it cannot and does not claim to cover — by the project's own stated convention (`internal/store/AGENTS.md`'s "the fake clientset resolves no names, execs nothing... those belong to `/check verify` against the real cluster") — is whether `recoverStranded` is reachable in the scenario it exists for, which is precisely the gap described above and precisely why `verify.md` left those two boxes for a real cluster.
