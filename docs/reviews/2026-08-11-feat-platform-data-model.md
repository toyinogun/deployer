## Summary

This lands the whole platform data model in one migration: nine SQLite tables, a Go domain package for the deployment state machine and slug derivation, an `internal/ids` package for prefixed ULIDs, and an `internal/store` package that owns every transaction. The design faithfully implements spec 0002: invariants (one in-flight deployment per app, valid states, permanent slugs, no orphans) are enforced by the database via CHECK constraints, partial unique indexes, and `ON DELETE RESTRICT`, not just by Go. `MarkHealthy` correctly closes the "torn release" window by doing the transition, event, release insert, and `current_release_id` update in one transaction, verified by a test that forces the release insert to fail and checks nothing else survived. The store test suite is exercised against a real SQLite file with no mocking, is unusually thorough (races, CHECK constraints, foreign keys, retention, migration up/down, pragma propagation across pooled connections), and the project already caught and fixed a real concurrency bug in `ids.New` during its own verify pass (documented in `verify.md`). `gofmt`, `go vet`, `golangci-lint`, and `go test -race ./...` are all clean. The few gaps found are minor: one untested error branch, a couple of small readability nits, and a config validation edge case.

## Minor

### 🟡 `Transition(..., domain.StateHealthy, ...)` guard is untested, `internal/store/deployments.go:151-155`
**Problem**: `Transition` explicitly refuses a caller trying to reach `healthy` directly (`"store: use MarkHealthy to reach healthy: %w", ErrIllegalTransition`), but no test in `internal/store/*_test.go` calls `Transition(ctx, id, domain.StateHealthy, ...)` to exercise this branch.
**Why it matters**: It is real branching, error-handling logic per the review guide's bar for `TESTS = configured`, and it is exactly the kind of guard that silently rots if `MarkHealthy` is refactored later (e.g., someone routes a caller through `Transition` for healthy "just this once").
**Suggested fix**: Add a small case (table-driven alongside `TestIllegalTransitionWritesNothing`, or its own test) that calls `Transition` to `domain.StateHealthy` from `deploying` and asserts `ErrIllegalTransition` plus zero new event rows.

### 🟡 `CreateApp`'s collision detection can misattribute a race as a slug collision, `internal/store/apps.go:38-51`
**Problem**: On a unique violation, `nameTaken` is queried *after* the failed insert to decide whether the error was a name collision (`ErrAppNameTaken`) or a slug collision (retry). If a second concurrent `CreateApp` call for the same account/name commits its insert in the gap between this failed insert and the `nameTaken` check, the check reports `true` even though the real cause under test would have been the slug — and conversely, in the very rare case the true collision was on name but a soft-delete of the colliding row races in between, the loop would spend a retry attempt as if it were a slug collision. Either way a caller sometimes gets a slightly wrong error classification (`ErrAppNameTaken` vs. exhausting slug retries) under concurrent creates of the same name.
**Why it matters**: Low likelihood (concurrent creates of the identical account+name pair), and the eventual outcome is still a rejection either way, so this is not a correctness bug in the sense of a wrong row being written — but the error a caller sees can be misleading during a genuine race, which matters for an agent that branches on the sentinel to decide whether to retry with a new name.
**Suggested fix**: Not blocking; worth a one-line comment noting the classification is best-effort under concurrent same-name creates, or move the disambiguation inside the same transaction as the insert if it turns out to matter in practice.

## Nits

- ⚪ `internal/store/deployments.go:97-98,129-133` (and similarly in `accounts.go`, `apps.go`, `uploads.go`): `now := s.now()` is computed once per call, but each `ids.New(..., s.clock.Now())` calls `s.clock.Now()` again independently rather than deriving from the already-computed instant. Harmless (both calls return the same value under `FixedClock`, and nothing reads time back out of an id per the `ids.New` doc comment), but it's an extra clock read per id and a small inconsistency in style worth a helper like `s.newID(prefix)` if this pattern keeps repeating across the package.
- ⚪ `internal/store/apps.go:57-66`, `nameTaken` drops to a raw `db.QueryRowContext` with an inline SQL string instead of a `sqlc` query like the rest of the package. Reads fine, but it's the one hand-written query with no compile-time regeneration, so a column rename elsewhere in the schema won't touch it. Consider giving it a `sqlc` query for consistency, or a comment explaining why it's hand-rolled (checking existence via an anonymous struct isn't worth codegen, or similar).
- ⚪ `docs/specs/0002-platform-data-model/index.md`, build plan item 8 ("Define the narrow per domain store interfaces in the consuming packages...") is unchecked while every other build-plan item is checked, and `scope.md` marks the whole "Build it" line done. There's nothing to consume the store yet (no use case package exists), so this is expected, but it's worth a one-line note in the spec or scope that item 8 is deferred to the first consuming slice rather than silently dropped.

## Strengths

- `MarkHealthy` genuinely closes the torn-release window: `TestMarkHealthyIsAllOrNothing` plants a conflicting release row to force the insert to fail mid-transaction and asserts the deployment state, event count, and `apps.current_release_id` are all unchanged — this is exactly the kind of test that proves a transactional invariant rather than just its happy path.
- The `ClaimNextDeployment` query (subquery pick + outer re-check, both under one `UPDATE`) is race-correct by construction given SQLite's single-writer model, and `TestClaimRaces` proves it directly with eight concurrent goroutines rather than trusting the SQL by inspection.
- The team caught and fixed a real bug during its own verify pass: `ids.New`'s monotonic entropy could reseed and reorder ids when concurrent callers with their own clocks interleaved out of timestamp order. The fix (pin to a high-water mark) is documented with its own regression tests (`TestOrderingSurvivesAnEarlierStamp`, `TestConcurrentCallersKeepDistinctOrderedIds`, `TestABackwardsStampNeverSortsBackwards`) and the failure is honestly recorded in `verify.md` rather than smoothed over.
- Every load-bearing invariant from the spec is enforced at the database layer as well as in Go: the CHECK on `state`, the partial unique index for one in-flight deployment per app, the `(upload_id) XOR (source_release_id)` CHECK, and `ON DELETE RESTRICT` everywhere are all independently exercised by tests that write raw SQL to bypass the Go layer (`TestDatabaseRefusesAnUnknownState`, `TestIndexRefusesASecondInFlightRow`, `TestDeploymentSourceIsExactlyOne`, `TestForeignKeysRestrict`).
- The secret-handling split (`ListConfigForResponse` vs. `ListForDeploy`) is enforced structurally (different SQL, different Go methods) rather than by a runtime flag a caller could forget to check, and `TestConfigReadPathsAreSplit` verifies both directions.

## Test coverage

Exceptionally thorough for a data-model slice: every acceptance criterion in spec 0002 (AC-1 through AC-18) has at least one named test cross-referenced in `verify.md`, concurrency is tested with real goroutines against a real SQLite file (not mocked), and constraint enforcement is tested by deliberately going around the Go layer with raw SQL. The two gaps are the untested `Transition`-to-`healthy` guard noted above (Minor) and the inherent best-effort nature of the `CreateApp` race-classification path (also noted above, low severity). No test asserts anything meaningless or tests only the happy path — several tests are explicitly structured to prove a negative (nothing was written) rather than just a positive.
