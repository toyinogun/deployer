## Summary

This range stands up the whole cluster foundation for spec 0003: `deploy/` (namespace, RBAC, admission policy, PVC, config, Deployment, Service, two Ingresses, the hand-applied hello-world app, and the ArgoCD/cert-manager GitOps pieces), the `/healthz` vs `/readyz` split in `cmd/deployer/main.go`, the new `internal/config` cluster settings, `Store.Ready`, and a CI job that publishes the image and pins its digest back into `deploy/deployment.yaml`. The Kubernetes surface is unusually careful: the narrow ClusterRole, the ValidatingAdmissionPolicy closing the two RBAC gaps that can't be scoped by name, digest-only image references, and pod hardening are all correct and internally consistent with the spec. The main gap is that `Store.Ready`'s "migrations still pending" branch — the exact case that keeps a half-migrated pod out of its Service — has no test anywhere in the range, despite `TESTS=configured` and this being the code AC-4 depends on. One narrow shutdown race in the new `health` type is worth hardening but is low practical impact.

## Major

### 🟠 `Store.Ready`'s pending-migration branch is untested, `internal/store/store.go:135`
**Problem**: `Ready` has two failure branches: the ping failing, and `HasPending` returning true. Every test that exercises `Ready` — `cmd/deployer/main_test.go`'s `TestHealthReady_okOnceTheDatabaseIsOpenAndMigrated` and `TestOpenMigrated_returnsAFullyMigratedStore` — opens a store, migrates it fully via `openMigrated`/`Store.Migrate`, and only then calls `Ready`. There is no test anywhere in `internal/store` or `cmd/deployer` that opens a store, applies migrations partway (or not at all) via the raw `goose.Provider`, and asserts `Ready` returns the `"migrations are still pending"` error.
**Why it matters**: This branch is the entire reason `Store.Ready` exists — it is what AC-4 depends on to keep a pod that boots mid-rollout, or against a database another version half-migrated, out of its Service instead of serving with a stale schema. An untested branch in the code the readiness probe calls is exactly the kind of gap the review guide calls Major for branching/error-handling logic under `TESTS=configured`.
**Suggested fix**: In `internal/store`, add a test that opens a store, runs the goose provider down (or stops short of `Up`), and asserts `Ready` returns an error whose message names pending migrations — mirroring the pattern `lifecycle_test.go` likely already uses for `MigrateDown`/`Migrate`.

## Minor

### 🟡 `health.close()` can race `health.open()`'s success path at shutdown, `cmd/deployer/main.go:159`
**Problem**: `close()` takes a single read-lock snapshot of `h.store` and returns immediately if it is `nil`. `open()` runs in its own goroutine and can still be mid-flight when shutdown starts: if `openMigrated` happens to succeed (e.g. an already-migrated, fast-opening database) in the narrow window after `ctx` is cancelled but before the loop's `select` is reached, `open()` will publish a non-nil `h.store` and return via the success path rather than the `<-ctx.Done()` branch, with no way for `close()` — which may have already run and seen `nil` — to ever close that handle.
**Why it matters**: In practice this is unlikely to fire (the derived `migrateCtx` usually fails fast once `ctx` is cancelled), and the process exits immediately afterward so the OS reclaims the fd, but a live `*sql.DB` handle around an open SQLite WAL file left uncleaned at shutdown is exactly the class of bug that is hard to reproduce and easy to dismiss until it shows up as a slow or unclean pod swap under `Recreate`.
**Suggested fix**: Either have `run()` join the `open()` goroutine before returning (so `close()` runs only after `open()` has definitely stopped touching `h.store`), or have `open()` check `ctx.Err()` under the same lock before publishing a late success and close the handle itself if the context is already done.

Nothing in this range actually creates a LimitRange from code yet, so it is not live-broken, but it is a real inconsistency between the accepted spec text and the ClusterRole that slice 1 will hit the moment it tries to compose one.

**Suggested fix**: Nothing to change in this range; confirm the `/architect cluster foundation` follow-up gets filed before slice 1 needs it, as the comment already says.

## Nits

- ⚪ `deploy/gitops/argocd-application.yaml:556`, the comment "Namespace is listed by name so the project cannot manage any other namespace object" is easy to misread as ArgoCD restricting by a specific namespace *name*. `clusterResourceWhitelist` restricts by resource *kind* (there's no such thing as a per-object-name whitelist entry); the actual protection for AC-15 is that a runtime-created `app-<slug>` namespace never appears under `deploy/` so ArgoCD never tracks it, which the surrounding prose already says correctly. Consider tightening the one sentence that doesn't.
- ⚪ `cmd/deployer/main_test.go:146`, `TestHealthOpen_keepsRetryingWhileTheDatabaseIsUnusable` waits a fixed `200 * time.Millisecond` for the first failed attempt to be recorded before cancelling. A slow CI runner could in principle race this, though the failure mode is just a flaky pass rather than a false failure, so it's low risk as written.

## Strengths

- The Kubernetes security surface is genuinely well thought through: the ClusterRole is short enough to read end to end, `deployer-app` is never bound cluster-wide, and the `ValidatingAdmissionPolicy` closes exactly the two gaps RBAC can't express (namespace name, rolebinding target) with a `failurePolicy: Fail` / `Deny` posture — and `verify.md` includes the exact `curl` probes to prove it holds, including the `kubectl auth can-i` caveat about the Tailscale operator masking identity.
- The `/healthz` vs `/readyz` split in `main.go` is exactly right for the stated invariant (liveness never touches the database) and `main_test.go` proves both halves of it directly, including that liveness keeps answering 200 while readiness is failing on a broken database — the scenario the whole design exists for.
- `internal/config`'s new quota settings are validated as real Kubernetes quantities via `resource.ParseQuantity` rather than treated as opaque strings, catching a malformed `DEPLOYER_APP_QUOTA_CPU` at boot instead of at the first `ResourceQuota` apply, with a test case for every failure mode (`config_test.go`'s `TestClusterSettingsRejectMalformedValues`).

## Test coverage

`internal/config`: fully covered — every new setting has a default test, an override test, and a malformed-value test naming the variable (AC-16). `cmd/deployer`: the new `health`/probe surface is covered thoroughly, including the retry loop under a permanently unusable path, the shutdown signal, and the liveness/readiness split under a real running server. `internal/store`: the one gap above — `Ready`'s pending-migration branch has no direct test in `internal/store`, only indirect coverage of the already-migrated path via `cmd/deployer`. The Kubernetes manifests and CI publish job are, correctly, not unit-testable from this repo; `verify.md` is the safety net for that surface and is thorough.
