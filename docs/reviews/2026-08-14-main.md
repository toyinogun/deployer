## Summary

This change is the test suite for spec 0013's web interface: a real SQLite-backed harness (`internal/web/harness_test.go`) drives the page surface through `internal/identity` and a real authenticator, faking only the two store/Kubernetes reads the package declares interfaces for. Coverage is genuinely good: CSRF, origin checking, ownership isolation, the failure-reason table, the serving-vs-last-deploy split, the leak crawl, and every admin/token write path are all exercised with real assertions rather than tautologies. `go test -race`, `gofmt`, `go vet`, and `golangci-lint` are all clean. The one real problem is a flaky test that fails nondeterministically about 1 in 16 runs; there is also a small, genuine coverage gap on the token-expiry validation branch.

## Major

### 🟠 Flaky CSRF-mutation test, `internal/web/routing_test.go:189-191`
**Problem**: `TestAnAuthenticatedPostNeedsItsSynchroniserToken/altered_by_one_character` builds its "altered" CSRF value as `strings.Repeat("a", 1) + good[1:]`, i.e. it forces the first hex character to `'a'`. The real CSRF token is a hex-encoded HMAC-SHA256 digest, so roughly 1 in 16 times the token's first character is already `'a'`, and the "altered" value is then byte-for-byte identical to the valid one. The request is accepted (200), the token *is* minted, and the subtest fails: `got 200, want 403`, plus the audit-row and mint-count assertions fail too. Confirmed empirically: 6 failures in 80 runs of `go test -run TestAnAuthenticatedPostNeedsItsSynchroniserToken -count=1 ./internal/web/...`, consistent with the 1/16 theoretical rate.
**Why it matters**: This is a security-relevant test (CSRF enforcement) that will intermittently red the CI gate on unrelated commits, train reviewers to reflexively re-run failing CI, and — the more important failure mode — the flakiness works in one direction only (false failures, never false passes), so it doesn't mask a real hole, but it does erode trust in "the suite is green" for exactly the guard this project treats as load-bearing.
**Suggested fix**: Force a genuine single-character alteration regardless of the original first byte, e.g. flip the first hex digit to something guaranteed different (`if good[0] == 'a' { ... use 'b' ... } else { use 'a' }`), or mutate a byte in the middle of the string with an explicit index and value, or XOR-flip a bit and re-encode. Any of these removes the dependency on the token's own randomness.

## Minor

### 🟡 No coverage for the invalid-expiry branch on token mint, `internal/web/tokens.go:47-57`
**Problem**: `tokenMint` has two distinct failure branches around `expires_days`: a `strconv.Atoi` parse failure (non-numeric input, handled inline with its own message) and a service-level refusal surfaced through `identity.CodeOf` (e.g. `identity.CodeInvalidExpiry`, mapped to 422 in `statusFor`). Spec 0013's API surface table for `POST /tokens` explicitly lists `422 invalid expiry` as a key error. Neither branch has a test in `internal/web/tokens_admin_test.go` or elsewhere in this suite; `routing_test.go`'s `TestStatusForPairsEachRefusalWithOneStatus` only pins the status-code mapping table, not that the handler actually reaches it for a bad `expires_days`.
**Why it matters**: TESTS = configured here, and this is untested error-handling logic on a page action, which the review guide weighs at least Minor (Major if it were security relevant — it isn't, since a rejected mint just re-renders the form). It's a small but real gap given the spec calls this error out by name.
**Suggested fix**: Add a case (or a small table test) posting `expires_days` as a non-numeric string and as a value the identity service refuses, asserting 422/422 and that no token was minted either time.

## Strengths

- The harness (`internal/web/harness_test.go`) is not a mock-everything harness: it runs a real SQLite file, the real `identity.Service`, and the real `auth.Authenticator`, so the session gate, the rate limiter, and the audit rows are exercised as they actually behave, not as a test's idea of them. Only the two reads the package has no cheap fixture for (app/release/config data, Kubernetes pods) are faked, and both are declared as narrow interfaces the production `Data`/`Pods` types also satisfy.
- `TestAnotherAccountsAppIsTheSameNotFoundAsAnUnknownOne` and the config-reveal equivalents assert *byte-identical* bodies for "belongs to someone else" vs "doesn't exist," which is the right bar for an ownership check that must not become an enumeration oracle — a weaker "both return 404" assertion would have missed a body that leaks which slugs exist.
- `TestNoPageOrLogLineCarriesACredential` captures the real `slog` default handler for the duration of the crawl and checks both response bodies *and* redirect `Location` headers against four categories of secret, which is exactly the AC-31 leak boundary as specified, not a narrower version of it.
- `TestEveryReasonCodeRendersASentenceBesideItsCode` walks every written reason code and separately exercises the drift case (`invented_later`), pinning the fallback-to-raw-code behavior that keeps a future `internal/domain/reason.go` addition from breaking the page instead of just trusting the fallback exists.

## Test coverage

Coverage of the acceptance criteria in scope (AC-2, AC-3, AC-5 through AC-26, AC-31) is thorough and the assertions are substantive rather than tautological — most tests assert on side effects (audit rows, token lists, session liveness) in addition to status codes. The two gaps found are: the flaky CSRF-mutation subtest above (a correctness problem in the test itself, not a coverage hole), and the untested invalid-expiry branch on token mint. AC-27 through AC-30 (visual design, motion, responsiveness, keyboard/no-JS reachability) are out of scope for a Go test suite by nature and are correctly left to the manual `/check verify` pass recorded in `verify.md`.
