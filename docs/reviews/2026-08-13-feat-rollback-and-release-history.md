## Summary

This change adds `list_releases` and `rollback_app` over the existing release table, restores both the image and the full configuration on a rollback, and closes two real production bugs found while verifying it against the cluster (a `WorkloadReady` check that read the old ReplicaSet's availability as the new one's, and quota-tracked `Create`s that were never preceded by a `Get`). The implementation matches the governing spec (0011) point for point: every acceptance criterion I checked has a corresponding code path and, in nearly every case, a test that pins it by name. The snapshot format change (`{value, secret}` per key, decoded per-key with a bare-string fallback for pre-existing rows) is implemented exactly as the spec's decision section describes, and the three-way `Drive` branch (top of `Drive`, the `queued` block in `run`, and `deployApp`'s image/config source) is exactly where the spec said the seams had to go. I found no correctness, security, or convention issues worth blocking on. The two items below are both nits.

## Nits

- ⚪ `internal/mcp/releases.go:143` and `internal/mcp/config.go:271`, the audit/refusal helper `denyConfig` is reused here for `rollback_app`'s refusals even though the action is not configuration. It behaves correctly (writes the audit row and returns `toolError`) and the pattern matches how `deploy_app` reuses `s.deny` for non-config refusals, so this is naming only, not a functional issue. A generically named helper (or a thin `denyRelease` alias) would read more clearly next to `rollback`, but it is not worth a change on its own.
- ⚪ `internal/mcp/releases.go:56`, `rollbackOutput` has no field for the release the rollback will mint (by design, per the doc comment, since nothing has run yet). Worth double-checking that agents calling this tool understand `state` is always `"queued"` and that they need a follow-up `deployment_status` call — the tool description does cover this, so this is just a note that the description is carrying real weight here and any future edit to the output shape needs to keep the description in sync (AGENTS.md's own rule about descriptions being contract).

## Strengths

- The layering discipline holds throughout: `internal/reconcile` never imports `client-go`, `net/http`, or the store; it declares `Deployments`/`Apps` interfaces and `internal/store/reconcileadapter.go` implements them. `internal/domain` stays pure.
- `internal/kube/kube.go`'s `WorkloadReady` rewrite is a genuinely good fix, with a doc comment that explains *why* each of the three comparisons is load-bearing (the same set `kubectl rollout status` makes), and `kube_test.go` has a table of six cases that would each catch a regression to the old `UpdatedReplicas > 0 && AvailableReplicas > 0` check.
- The quota fix in `ApplySecret`/`ApplyWorkload` (read-before-write for quota-tracked objects) is narrowly scoped to Secrets and Services and explicitly leaves Deployments and Ingresses alone, matching the stated reason (only the former are quota tracked), and is pinned by `TestApplyingOverExistingObjectsIssuesNoCreate`, which asserts on the actual client-go action list rather than just the outcome.
- The config snapshot decoder (`decodeSnapshot` in `internal/store/deployments.go`) is genuinely careful: per-key rather than per-document decoding, a documented reason for defaulting an unflagged key to secret (leaking is worse than over-hiding), and `TestAnOldShapeSnapshotRestoresEveryKeyAsSecret` proves it against a snapshot planted via raw SQL rather than through any Go path that could no longer produce that shape.
- `reconcile/rollback_test.go` is unusually rigorous for a "does the happy path work" suite: it hands a registry stub that errors if asked to resolve anything (`errNoRegistry`), so the tests prove a rollback never talks to the registry rather than merely observing the final state. `TestARollbackRestoresTheReleasesConfiguration` checks the Secret in the fake cluster, the pod-template checksum, and `app_config` all in one test, which is exactly the AC-12/AC-13 fidelity claim the spec makes.
- AC-23 ("both tools exercised through a real MCP client/server session") is satisfied correctly even though `internal/mcp/wire_test.go` itself wasn't touched: `releases_test.go` calls the `callOverTheWire` helper that already lives there, which is precisely the pattern AGENTS.md now documents ("the cases live beside the feature rather than all in that one file").
- The two follow-up fixes (`e02a845`, `1222412`) were caught by driving the actual feature against the real cluster, not by static review, and both came with a unit test afterwards — consistent with the project's own stated practice ("each one that bites is worth a unit test pinning the value afterwards").
