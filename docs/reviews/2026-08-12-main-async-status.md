## Summary

This lands spec 0005 cleanly: `deploy_app` now returns immediately with a `queued` row, a new `deployment_status` tool reads back state, timeline, release, and supersession off already-written rows, and a watchdog inside the single-goroutine reconcile loop closes the one way a deployment could sit in flight forever. The load-bearing invariants hold up under inspection: the loop is still the only writer of deployment state (the new `ErrTerminal`/`ErrNotInFlight` plumbing lets a drive notice it was superseded and stop rather than write over it), the budget is measured from `created_at` so a resumed deployment never gets a fresh window, and `deployment_events.detail` is dropped at the one projection boundary rather than at each write site. `go build`, `go vet`, `golangci-lint run`, `gofmt -l .`, and `go test -race ./...` are all clean, and `sqlc generate` produces no diff. The concurrency reasoning (why the deadline lives inside the loop, why two enforcement points and not one) is unusually well tested for exactly the races it claims to close. Two things worth fixing before or shortly after merge, both minor: `deployment_status` folds genuine internal faults into `deployment_unknown` rather than `internal`, and the spec's explicitly named "blocked loop" test scenario (queued-behind-a-long-drive expiring while the drive is still going) has no direct test.

## Minor

### 🟡 A genuine internal fault while resolving a deployment or app is reported and audited as `deployment_unknown`, `internal/mcp/status.go:52-69`
**Problem**: `resolveDeployment` wraps *every* error from `s.deployments.Get`, `s.deployments.LatestForApp`, and `s.apps.ByName` — not just the legitimate "not found" and "belongs to another account" cases — and `status()` passes all of them to `denyStatus`, which unconditionally emits `domain.ReasonDeploymentUnknown` and writes an audit row with that reason. A transient store fault (a busy SQLite handle, a context deadline, anything `MCPDeployments.Get`/`LatestForApp` don't specifically map to `ErrNotFound`) therefore reaches the caller as "no deployment matches that id or name" and lands in `audit_log` as a denial, rather than as `ReasonInternal`. Compare this to the rest of the same file: an `s.apps.Get(ctx, dep.AppID)` failure *after* `resolveDeployment` succeeds, and any failure inside `project`, both correctly map to `toolError(auth.ActionStatus, domain.ReasonInternal, err)`. `deploy_app`'s `resolveApp` follows the same "only a real not-found maps to the specific code" pattern (`internal/mcp/mcp.go:280`).
**Why it matters**: An agent polling `deployment_status` during a real fault gets told the id or name is wrong, which is the wrong signal — it might stop polling a deployment that is actually still running, or "fix" an id that was never wrong. It also pollutes `audit_log`: AC-10's denied-row semantics assume a denial reflects an actual access decision, not a masked fault, and anyone querying that table for genuine unauthorized/unknown attempts (the audience AC-9/AC-10 are written for) gets false positives mixed in. The cause is still logged via `toolError`'s `slog.Error`, so it isn't fully invisible to operators, but the caller-visible reason and the durable audit trail are both misleading.
**Suggested fix**: In `resolveDeployment`, only wrap the true "not found"/"forbidden" outcomes into the error that reaches `denyStatus` with `ReasonDeploymentUnknown`; anything that isn't `errors.Is(err, ErrNoDeployment)` or `errors.Is(err, ErrNoApp)` should be reported the way `status()` already reports its other internal faults, with `toolError(auth.ActionStatus, domain.ReasonInternal, err)` and no audit row (or, if an audited fault is wanted, a distinct outcome from a denial).

### 🟡 The spec's "watchdog and a blocked loop" scenario has no test, `internal/reconcile/watchdog_test.go`
**Problem**: Spec 0005's Critical test scenarios names a specific case worth locking down: "with one deployment driving long ... and a second app's deployment sitting `queued` past its own budget, the queued one is failed once the drive returns, and the driving one is failed at its own phase boundary. This is the scenario that proves what AC-14's two enforcement points actually cover." The current suite tests the phase-boundary check alone (`TestTheDrivenDeploymentIsFailedAtItsOwnBudget`) and the sweep alone (`TestTheSweepFailsAnOverdueDeploymentAndDeletesItsBuild`, `TestADeploymentPastItsBudgetIsFailedWithoutBeingDriven`), but never both together with a long-running drive holding the tick while a second, separately-overdue deployment waits behind it.
**Why it matters**: TESTS is configured, so untested acceptance-relevant behavior is a gap by the project's own bar, and this specific scenario is the one the spec calls out as proof that the sweep and the phase-boundary check are not redundant with each other — i.e., that a drive genuinely can starve a queued row for the length of its own budget, and that the sweep genuinely can't reach a row the loop is holding. Nothing currently exercises both mechanisms in the same test to confirm neither accidentally masks a gap in the other (e.g. a queued deployment never getting swept at all while something else drives).
**Suggested fix**: Add a test with two deployments for two apps: one claimed and driven with a build that never completes (as `buildNeverEnds` already provides), and a second, separate app's deployment left `queued` with a budget that expires while the first is still driving. Assert the second is untouched until the first drive returns, then gets failed with `timeout` on the very next tick's sweep, and the first is independently failed at its own phase boundary.

## Strengths

- The single-goroutine argument in the rationale is proven, not just asserted: `Run` ticks sequentially with no second goroutine driving deployments, so `expireOverdue` (before `ClaimNext`) and `Drive` (holding the tick) genuinely cannot race each other, and the tests for supersession mid-drive (`supersede_test.go`) exercise the one real concurrent writer that does exist — the MCP handler's `CreateDeployment` — against a drive in progress, at two different phase boundaries (a plain `Transition` refusal and a `MarkHealthy` refusal), asserting zero error-level logs for what is normal platform behavior.
- `superseded_by`'s derivation is tested against its actual failure mode rather than a token case: `TestSupersededByIsOrderedByIdNotTimestamp` creates three deployments that provably share one `created_at` (asserted, not assumed) under the injected clock, and proves the `id` ordering resolves them correctly, which is exactly the tie a `created_at`-ordered query would get wrong.
- `deployment_events.detail` is dropped at exactly one projection boundary (`MCPDeployments.Events`) rather than at each write site, and `TestTheStatusProjectionDropsEventDetail` proves both halves: the detail is still on the stored row (the loop didn't stop recording it) and absent from every field of the projected timeline.

## Test coverage

Well covered for the core state machine and concurrency claims: the watchdog's two enforcement points, the supersession race at two different phase boundaries, the budget-from-`created_at` resume behavior, the status payload's per-state shape (including the supersession race where the successor row isn't visible yet), and the auth/audit symmetry across unknown-id, other-account-id, unknown-name, and never-deployed-name are all directly tested. The `sqlc generate` no-diff and reason-set-is-exactly-eleven checks in `verify.md`'s Commands section are satisfied. Two gaps: the "blocked loop" scenario above, and `verify.md` itself still marks the real-cluster resume-budget step and the root-image `reason`/`message` step as unchecked — expected for a slice that hasn't had `/check verify` run against the cluster yet, not a defect in this diff.
